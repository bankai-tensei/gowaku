# gowaku コーディング規約

[English](CODING_STYLE.md)

対象は gowaku 本体と examples である。全体の構造は [ARCHITECTURE.ja.md](ARCHITECTURE.ja.md) を参照。

この規約は、迷ったときに参照するためのものである。ここに書かれていないことは [Effective Go](https://go.dev/doc/effective_go) と
[Go Code Review Comments](https://go.dev/wiki/CodeReviewComments) に従う。
規約から外れる必要が生じたら、その箇所にコメントで理由を書くか、規約のほうを改める。

---

## 1. 五つの原則

1. **読む人のために書く。** 賢いコードより退屈なコードを選ぶ。1 ファイルには 1 つの概念、1 つの関数には 1 つの仕事。
2. **依存は下向きのみ。** 上の層が下の層に依存するのはよいが、逆は禁止する（§3）。違反は lint で機械的に検出する。
3. **ホットパスではアロケーションしない。** フレームごとに実行されるコードは、`go test -bench` で allocs/op = 0 であることを確認する（§7）。
4. **unsafe と OS 呼び出しは境界の内側に閉じ込める。** `platform/*` と `gpu/*` の外では `unsafe`、`syscall`、`purego` を使わない（§8）。
5. **GPU なしでテストできるようにする。** `core` / `layout` / `paint` / `text` / `theme` / `motion` は、GPU もウィンドウもない環境で `go test ./...` が通るようにする（§10）。

## 2. ツールと自動チェック

| 対象 | コマンド | 実行するタイミング |
|------|----------|------|
| フォーマット | `gofmt -s -w .` と `goimports -local github.com/bankai-tensei/gowaku -w .` | 保存時（エディタ） |
| 静的解析 | `go vet ./...` と `golangci-lint run` | コミット前、CI |
| テスト | `go test -race ./...` | コミット前、CI |
| GPU テスト | `go test -tags gpu ./gpu/...` | ローカルのみ |
| ベンチマーク | `go test -bench . -benchmem -run ^$ ./core/ ./text/ ./render/` | ホットパスを変えたとき |
| シェーダー生成 | `go generate ./gpu/...` | シェーダー変更時 |

- lint の設定はリポジトリ直下の `.golangci.yml` にある。層の依存違反は `depguard` が検出する。
- `//nolint` は行単位で使い、必ず理由を書く（例: `//nolint:gocritic // vtable call needs raw uintptr`）。ファイル単位の nolint は禁止する。
- 生成したファイルには先頭に `// Code generated by <tool>; DO NOT EDIT.` を付け、手で編集しない。

## 3. パッケージと依存方向

### 3.1 層と許可される import

```
widgets/* ─→ core, layout, paint, icons, text, theme, motion, input, semantics, geom（中は 6 段。上の段は下の段だけ。ADR 0081）
motion   ─→ core, geom
theme    ─→ text, paint(型のみ), geom
layout   ─→ core, paint, input, semantics, geom
core     ─→ paint, text, input, semantics, geom
text     ─→ paint(型のみ), geom
icons    ─→ paint, geom（パスとして描いた標準のアイコン。ADR 0127）
paint    ─→ geom
render   ─→ paint, text, gpu, geom
gpu      ─→ platform(NativeHandle のみ), geom
platform ─→ input, semantics, geom
semantics ─→ geom（アクセシビリティのツリー。core と platform の両方から見える。ADR 0042）
input    ─→ なし
geom     ─→ 標準ライブラリのみ
gowaku(ルート) ─→ すべて（アプリとウィンドウの入り口だけを持ち、ウィジェットや下の層の型を再エクスポートしない。ADR 0081）
```

- `core` は `layout` を知らない。標準の RenderObject（Padding, Flex, Stack）は `layout` にあり、`core.RenderObject` インターフェースを実装する側である。
- `core` / `layout` / `paint` / `text` / `theme` / `motion` は **`gpu` と `platform` を import しない**。「GPU なしでテストできる」のはこのためである。
- `render` だけが `paint` の DisplayList と `gpu` の両方を知る。
- 横方向（同じ段どうし）の import も禁止する。必要になったら、共通部分を下の層に移す。
- アプリは、使う層のパッケージ（`widgets/basic`, `widgets/control` など）を直接 import する。ルートに置く型の別名は、どのウィジェットでも使う `Widget`, `BuildContext`, `State` などに限る。ドットインポートは使わない。

### 3.2 パッケージの作法

- ディレクトリ名とパッケージ名は一致させる。小文字、単数形で、アンダースコアは使わない（`widgets` だけは例外的に複数形）。
- 識別子にパッケージ名を繰り返さない。`paint.PaintCanvas` ではなく `paint.Canvas` とする。
- 外部から使わせないものは `internal/` に置く（`internal/testutil`、`internal/cmd/*` など）。
- 各パッケージに `doc.go` を置き、パッケージコメントにその層の責務と、import してはいけないものを書く。
- `init()` で副作用を起こさない。GPU バックエンドの登録もしない（バックエンドは `gowaku.Run` が明示的に選ぶ）。
- パッケージレベルの可変変数は禁止する。例外は `app` のプロセス内 GPU デバイスと、`-tags gowakudebug` の検査フラグだけで、どちらも `doc.go` に列挙する。

## 4. 命名

### 4.1 一般

- Go の慣習に従う。`MixedCaps` を使い、略語はすべて大文字かすべて小文字にする（`ID`, `HTTP`, `hwnd`, `dpi`）。
- getter に `Get` を付けない。`w.GetSize()` ではなく `w.Size()` とする。setter は `SetX` とする。
- bool は肯定形で名付ける（`Enabled`, `Visible`）。`Disabled` や `Hidden` は作らない。例外は、選択肢の型（`RadioOption`、`DropdownOption`）の `Disabled` で、ゼロ値の選択肢が無効にならないようにするためである（ADR 0054）。もう 1 つは `field.Input` の `Disabled` で、自分で文字列を持つので、`Button` のようにコールバックが nil であることを無効の意味にできないためである（ADR 0143）。
- 単位は型で表す。時間は `time.Duration`、長さは論理ピクセルの `float32` で表し、`WidthPx` のような接尾辞は付けない。物理ピクセルを扱う場所（`platform`, `gpu`）に限り、名前に `physical` を含める。
- 列挙は型付き定数と `String()` で表す。
  ```go
  type Axis uint8
  const (
      Horizontal Axis = iota
      Vertical
  )
  ```
  ゼロ値が最も自然な既定値になるように順番を決める。

### 4.2 よく使う略語（これ以外は略さない）

| 略語 | 意味 | 使う場所 |
|------|------|----------|
| `ctx` | `BuildContext` | Build 関数の引数 |
| `cv` | `*paint.Canvas` | Paint 関数の引数 |
| `c` | `layout.Constraints` | Layout 関数の引数 |
| `el` | `Element` | core 内部 |
| `ro` | `RenderObject` | core / layout 内部 |
| `w` | `Widget` または `Window` | 文脈で一意なときだけ |
| `pos`, `off`, `sz` | Offset, Offset, Size | 局所変数 |
| `rr` | `RRect` | 局所変数 |
| `dt` | 経過時間 | motion |

### 4.3 なじみのある名前

UI の開発者がすでに知っている名前を優先する：`Padding`、`Row`、`Column`、`Expanded`、`Stack`、`State`、`Build`、`Key`。RenderObject の名前は `Render` で始める（`RenderPadding`）。幾何の型は `geom` に置く（`Offset`、`Size`、`Rect`、`RRect`、`Color`、`Insets`）。どこでも null を許すフィールドや、コピー用の補助関数のような、ほかの言語の書き方は持ち込まない。代わりに、**ゼロ値を意味のある既定値** にする。

## 5. 型と API 設計

### 5.1 Widget

- Widget は **値型の構造体** とし、ポインタで渡さない。生成した後は変更しない。
- フィールドは公開し、オプションはすべてフィールドで表す。コンストラクタ関数は作らない（`VStack` などのヘルパは例外。§5.3）。
- **ゼロ値のまま使える** ようにする。`Text{}` は空文字列を描き、`Padding{}` は余白なしで子を描く。必須フィールドが未設定のときに panic してよいのは、`Child` のように構造上必須のものだけである。
- コールバックの名前は `On` で始める（`OnPress func()`, `OnChange func(string)`）。引数が 2 つを超える場合はイベント構造体にまとめる。
- 子は `Child Widget`（単数）か `Children []Widget`（複数）とし、それ以外の名前は使わない。

### 5.2 インターフェース

- インターフェースは小さく保ち、使う側のパッケージで定義する。メソッドは 1〜3 個が目安である。
- 引数や戻り値に `any` を使わない。例外は `Key` だけである。
- reflect を使ってよいのは、**型の同一性の比較** と `Inherited[T]` の型キーだけである。構造体のフィールドの列挙やタグの読み取りは禁止する。
- ジェネリクスは reflect を避けるために使う（`Tween[T]`, `Inherited[T]`）。見た目がよいからという理由では使わない。

### 5.3 関数と引数

- 引数が 4 つを超えたら、オプション構造体にまとめる。関数オプションパターン（`WithX(...)`）は使わない。構造体リテラルのほうが差分比較と相性がよいからである。
- メソッドチェーン（`.Spacing(8).Children(...)`）は作らない。ただし、値を 1 つだけ差し替えたコピーを返す単発のメソッド（`Color.WithAlpha`、`TextStyle.WithColor`）は、チェーンにも関数オプションにも当たらない。こうしたメソッドはよく変更するフィールドにだけ用意し、それ以外はコピーしてからフィールドに代入する（ADR 0031）。
- 可変長引数のヘルパ（`VStack(a, b)`）は、対応する構造体を返すだけの 1 行の関数とし、`widgets/basic/helpers.go` にまとめる。
- `context.Context` は使わない。UI にはリクエストスコープがないからである。キャンセルが必要なら `Ticker` と `Dispose` で表現する。
- 戻り値で `(T, bool)` と `(T, error)` を混在させない。見つからないことが正常な結果なら `bool`、失敗を表すなら `error` を使う。

### 5.4 構造体

- フィールドは、公開の設定 → 公開の状態 → 非公開の順に並べる。メモリ配置のパディングを気にするのは `gpu` のインスタンス構造体と `platform` の ABI 構造体だけで、これらには `unsafe.Sizeof` のテストを付ける（§8）。
- 埋め込みは is-a の関係にあるときだけ使う（`StateBase`, `RenderBase`）。便利だからという理由では埋め込まない。
- `sync.Mutex` は埋め込まない。`mu` という名前のフィールドにし、保護する対象の直前に置く。

## 6. エラーと panic

初期化の失敗は `error` で返し、実行中の致命的なエラーでは `panic` する。

- **error を返す場所**: `Run`、`platform.CreateWindow`、`gpu.New*`、`CreateTexture`、フォントの読み込み、画像のデコード。
- **panic する場所**: フレーム中の `DEVICE_LOST`、API の契約違反（Build 中の SetState、UI ゴルーチン以外からの SetState、comparable でない Key）。
- panic のメッセージは `gowaku: ` で始め、どの契約に違反したかを書く。
  ```go
  panic("gowaku: SetState called during Build; move the call to a callback or InitState")
  ```
- ライブラリの内部で `recover` しない。アプリのコードで起きた panic はそのまま伝播させる。
- error は `fmt.Errorf("d3d11: create swapchain: %w", err)` のように、先頭にパッケージ名を付けてラップする。文頭は小文字にし、末尾にピリオドを付けない。
- 種類を判別する必要があるエラーは、`var ErrNoGPU = errors.New("gowaku: no compatible GPU found")` のように sentinel error として公開し、`errors.Is` で比較できるようにする。
- error を無視するときは `_ = f()` と書き、横に理由をコメントする。`errcheck` が検出するので、黙って無視することはできない。
- `log` パッケージは使わない。ライブラリのログは `log/slog` の既定ロガーに `Debug` レベルで出力し、出すのは `platform` と `gpu` の初期化時だけにする。ホットパスでは一切出力しない。

## 7. パフォーマンス規約（ホットパス）

ホットパスとは、**フレームごとに実行される可能性のあるコード** を指す。reconcile、Layout、Paint、DisplayList から Batch への変換、テキストレイアウトのキャッシュヒット時の経路、ヒットテスト、Ticker による値の更新がこれに当たる。

- **アロケーションしない。** スライスは `s = s[:0]` で再利用する。フレームをまたいで使うバッファは構造体のフィールドに保持する。
- 各ホットパスに `Benchmark*` を用意し、`b.ReportAllocs()` で **allocs/op = 0** であることを確認する。0 にできない箇所は、ベンチマークのコメントに理由を書く。
- `fmt.Sprintf`、`strings.Builder` 以外による文字列の結合、`interface` への変換を伴う `any` 引数、ループ内の `defer`、順序に依存する `map` のイテレーションは使わない。
- 浮動小数点数は **float32** に統一する。`math` パッケージは float64 を扱うので、`geom` に用意した `Sqrt32`, `Abs32`, `Floor32` などを使う。
- `reflect.TypeOf` は reconcile での型の比較にだけ使い、結果は Element にキャッシュする。
- テキストは `(text, style, maxWidth)` をキーにキャッシュする。キャッシュミスの経路はホットパスに含めない（シェイピングではアロケーションしてよい）。
- 一方で、早すぎる最適化もしない。ホットパスの定義に当てはまらないコードでは、読みやすさを優先する。

## 8. unsafe / syscall / purego 規約

これらを使ってよいのは `platform/win32`, `platform/x11`, `platform/wayland`, `platform/cocoa`, `gpu/d3d11`, `gpu/vulkan`, `gpu/metal` だけである。他のパッケージで import すると `.golangci.yml` の `depguard` が検出する。

- **unsafe を使う箇所には、それぞれコメント** で、なぜ必要なのかとポインタの寿命を書く。
  ```go
  // pData must stay alive until Unmap; it is pinned by the pinner below.
  ```
- **C に渡す Go のポインタ** は、呼び出しの間だけ有効とみなす。呼び出し後も C 側で保持される場合は `runtime.Pinner` で固定し、`Unpin` する場所を明示する。呼び出しの直後には `runtime.KeepAlive` を置く。
- **ABI 構造体**（`D3D11_TEXTURE2D_DESC`, `VkSwapchainCreateInfoKHR`, `XEvent` など）には構造体ごとにテストを書き、`unsafe.Sizeof` を C でのサイズと比較する。注意の必要なフィールドについては `Offsetof` も確認する。
- **ハンドルには型を付ける**（`type HWND uintptr`, `type VkDevice uintptr`）。関数のシグネチャに生の `uintptr` を出さない。`platform` より上の層に渡すのは `NativeHandle` インターフェースだけである。
- **COM**: vtable のインデックスは定数にし、インターフェース名とメソッド名をコメントに書く。
  ```go
  const (
      iDXGISwapChain_Present       = 8  // IDXGISwapChain::Present
      iDXGISwapChain_GetBuffer     = 9  // IDXGISwapChain::GetBuffer
  )
  ```
  `AddRef`/`Release` の対応はメソッドの中で完結させる。参照を保持し続ける構造体には `Release()` メソッドを用意し、呼び忘れは `gowakudebug` タグで検出する。
- **purego**: `purego.Dlopen` は `sync.Once` を使い、1 つのライブラリにつき 1 回だけ呼ぶ。シンボルは起動時にまとめて解決し、見つからないものがあれば `error` で返す（go-vk の「nil を呼び出してクラッシュする」問題を繰り返さない）。
- OS の構造体やフラグの定数には、公式ヘッダの名前をそのまま使う（`WM_IME_COMPOSITION`, `VK_IMAGE_LAYOUT_PRESENT_SRC_KHR`）。Go 風に名前を変えない。検索できることを優先する。

## 9. 並行性

UI はメインゴルーチン専用である（[ARCHITECTURE.ja.md](ARCHITECTURE.ja.md) のスレッドモデルを参照）。

- `core` / `layout` / `paint` / `widgets` / `motion` の中では **ゴルーチンを起動しない**。`sync` も使わない。
- ゴルーチンをまたぐのは、`app.Post` のキューと `gpu` のテクスチャのアップロードだけである。`sync.Mutex` / `chan` を使うのもこの 2 か所に限る。
- 公開型の doc コメントには **ゴルーチン安全かどうかを明記** する。書いていなければ、UI ゴルーチン専用とみなす。
  ```go
  // Post schedules fn to run on the UI goroutine. It is safe to call from any goroutine.
  ```
- `-tags gowakudebug` を付けると、`SetState` を呼んだゴルーチンを検査する。検査には `runtime` のゴルーチン ID を使わず、UI ゴルーチンだけが持つ `goroutineToken` を `sync/atomic` で比較する。
- `core` / `motion` では `time.Now()` を直接呼ばない。`motion.Clock` インターフェースを注入し、テストでは固定の時刻を使う。

## 10. テスト

- `go test ./...` は **GPU もウィンドウもない環境で通る** ようにする。GPU が必要なテストには `//go:build gpu` を付け、`gpu/` 以下に置く。
- テーブル駆動テストを基本とする。ケース名は日本語でもよい（`t.Run("行頭禁則: 句点", ...)`）。
- テスト名は `Test<対象>_<状況>` とする（`TestReconcile_KeyedReorder`, `TestJLReq_LineStartProhibition`）。
- **golden**: `internal/testutil.Render(widget, size)` が返す DisplayList のテキスト表現を、`testdata/<name>.golden` と比較する。更新は `go test -update` で行う。差分が出たら、それが意図した変更かどうかを PR で説明する。
- 日本語組版のテストでは、「文字列と幅から行分割への対応」の表を golden にする。
- `time.Sleep` は使わず、時刻は `Clock` で注入する。
- ヘルパには `t.Helper()` を付ける。アサーションライブラリは導入しない。`if got != want { t.Errorf("got %v, want %v", got, want) }` で十分である。
- ベンチマーク名は `Benchmark<対象>_<規模>` とする（`BenchmarkReconcile_10kNodes`）。`b.ReportAllocs()` は必須である。
- カバレッジの数値目標は設けない。その代わり、reconcile、Layout、jlreq の各規則、HCT の 4 つについては境界値を網羅する。

## 11. コメントとドキュメント

- **doc コメントは英語で書く**。GitHub で公開するライブラリとして godoc が読まれるからである。1 文目は識別子の名前で始める（例: `// Padding insets its child by the given Insets.`）。
- 実装内のコメントも英語に統一する。日本語で書きたい設計の背景は `docs/ADR/` に書き、コードからは `// See docs/ADR/0003-stencil-clip.md` のように参照する。
- コメントには「何を」ではなく **「なぜ」** を書く。コードを読めば分かることは書かない。
- TODO には `// TODO(#123): ruby annotation` のように issue 番号を付ける。担当者の名前は書かない。
- 公開する識別子には例外なく doc コメントを付ける。付け忘れは `revive` の `exported` ルールで検出する。
- 主要な公開 API（`Run`, `StatefulWidget`, `AnimatedContainer`, `Text`）には `Example*` テストを付ける。これは godoc に表示される。

## 12. ファイル構成

- 1 ファイルには 1 つの概念を置く。ウィジェットなら `widgets/control/button.go` と `widgets/control/button_test.go`、RenderObject なら `layout/padding.go` のようにする。
- ファイル内の順序は、パッケージコメント（`doc.go` にある場合は省略）→ import → 定数 → 型 → コンストラクタ → メソッド（公開 → 非公開）→ ヘルパ関数とする。
- 500 行を超えたら分割を検討する。`command.go` のような巨大なファイルは、生成物にだけ許す。
- プラットフォーム固有のファイルは、ビルドタグではなく **ファイル名の接尾辞** で分ける（`window_windows.go`, `window_linux.go`）。タグが必要なのは、`gpu` テストの `//go:build gpu` と `gowakudebug` だけである。
- シェーダーは `gpu/<backend>/shaders/` に、`sdf.frag.glsl` / `sdf.ps.hlsl` のように役割と言語が分かる名前で置く。コンパイル済みのバイナリは、同じ名前に `.spv` / `.dxbc` を付けて隣に置く。`go:embed` は 1 か所（`shaders.go`）にまとめる。

## 13. Git

- ブランチには `fix-ime-caret`, `table-sort` のように内容を表す名前を付ける。main には動く状態のものだけを入れる。
- コミットメッセージは Go 本体の流儀に従い、`パッケージ名: 小文字で始まる要約` とする。
  ```
  core: add keyed child reconciliation

  Match the children from both ends first, then look up the
  middle by key. See docs/ADR/0002-reconcile.md.
  ```
  複数のパッケージにまたがるなら `core, layout: ...`、全体に関わるなら `all: ...` とする。
- 設計上の判断は `docs/ADR/NNNN-<slug>.md` に書く。形式は「背景 / 選択肢 / 決定 / 結果」で、1 つの判断につき 1 ファイルとし、決定した日付を入れる。
- 1 つのコミットには 1 つの意図だけを含める。フォーマットだけの変更は別のコミットにする。

## 14. 禁止事項（まとめ）

| 禁止 | 代わりに |
|------|----------|
| `init()` の副作用 | `Run` からの明示的な初期化 |
| パッケージレベルの可変変数 | 構造体のフィールド。例外は §3.2 |
| `any` の引数・戻り値（`Key` 以外） | 具体型かジェネリクス |
| 構造体を走査する reflect | 明示的なコード |
| `context.Context` | `Ticker` / `Dispose` |
| 関数オプション、メソッドチェーン | 構造体リテラル |
| `core` / `layout` 等でのゴルーチン、`sync` | `app.Post` |
| `time.Now()`（`core` / `motion`） | `motion.Clock` |
| `log` パッケージ、ホットパスのログ | `slog.Debug`（初期化時のみ） |
| ライブラリ内の `recover` | 伝播させる |
| `//nolint` の理由なし使用、ファイル単位の nolint | 行単位 + 理由 |
| `platform` / `gpu` 外の `unsafe` / `syscall` / `purego` | 境界に閉じ込める |
| 生の `uintptr` ハンドルを上の層へ | `NativeHandle` |
| `WidthPx` のような単位接尾辞 | 型と文脈 |
| `Get` 前置の getter、否定形 bool | `X()`, `Enabled` |

## 15. コード例: 規約に沿った Widget 一式

```go
// widgets/basic/padding.go

package basic

import (
    "github.com/bankai-tensei/gowaku/core"
    "github.com/bankai-tensei/gowaku/layout"
)

// Padding insets its child by the given Insets.
// The zero value draws the child without any inset.
type Padding struct {
    Insets layout.Insets
    Child  core.Widget
}

// Key implements core.Widget. Padding is never keyed directly; wrap it with Keyed.
func (Padding) Key() core.Key { return nil }

// CreateRenderObject implements core.RenderWidget.
func (p Padding) CreateRenderObject() core.RenderObject {
    return &layout.RenderPadding{Insets: p.Insets}
}

// UpdateRenderObject implements core.RenderWidget.
func (p Padding) UpdateRenderObject(ro core.RenderObject) {
    rp := ro.(*layout.RenderPadding)
    if rp.Insets != p.Insets {
        rp.Insets = p.Insets
        rp.MarkNeedsLayout()
    }
}
```

```go
// layout/padding.go

package layout

import (
    "github.com/bankai-tensei/gowaku/core"
    "github.com/bankai-tensei/gowaku/geom"
    "github.com/bankai-tensei/gowaku/paint"
)

// RenderPadding lays out a single child inset by Insets.
type RenderPadding struct {
    core.RenderBase
    Insets Insets
    child  core.RenderObject
}

// Layout implements core.RenderObject.
func (r *RenderPadding) Layout(c Constraints) geom.Size {
    if r.child == nil {
        return c.Constrain(r.Insets.Size())
    }
    inner := c.Deflate(r.Insets)
    sz := r.child.Layout(inner)
    r.child.SetOffset(geom.Offset{X: r.Insets.Left, Y: r.Insets.Top})
    return c.Constrain(sz.Add(r.Insets.Size()))
}

// Paint implements core.RenderObject.
func (r *RenderPadding) Paint(cv *paint.Canvas, off geom.Offset) {
    if r.child != nil {
        r.child.Paint(cv, off.Add(r.child.Offset()))
    }
}
```

要点は次のとおり。Widget は値型でゼロ値のまま使える。RenderObject は名前の先頭に `Render` を付け、`RenderBase` を埋め込む。更新時は変化があるときだけ `MarkNeedsLayout` を呼ぶ。`Paint` はアロケーションしない。公開する識別子にはすべて doc コメントを付ける。
