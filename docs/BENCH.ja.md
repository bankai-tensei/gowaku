# ベンチマーク結果: gowaku、Gio、Cogent Core

同じシナリオ（起動、アイドル、1 万行のスクロール、100 個の同時アニメーション、リサイズ）を 3 つのライブラリで実装し、プロセスの外から同じ方法で計測した。コードと手順は [examples/bench](../examples/bench/README.ja.md) にある。

負けた項目も隠さずに載せている。

[English](BENCH.md)

## Windows

計測日: 2026-11-10。生データは [results/windows-2026-11-10.json](../examples/bench/results/windows-2026-11-10.json)。

### 環境

| 項目 | 値 |
|---|---|
| PC | Windows 11、i7-12700H、Iris Xe + RTX 3050 Ti、1920×1200 / 60Hz、倍率 150% |
| Go | 1.27.3 |
| 比較対象 | Gio v0.10.3、Cogent Core v0.5.27 |
| 回数 | 3 回の中央値。起動のみ 15 回の中央値 |

Linux では 3 者の比較をしていない。Linux の検証環境には実 GPU がなく、ソフトウェア実装の Vulkan で他のライブラリと比べても意味がないからである。代わりに、gowaku 単体の参考値を後述する。

### 結果

太字はその行で最もよい値を示す。差が計測のばらつきの範囲内なら太字にしていない。

| 項目 | gowaku | Gio | Cogent Core |
|---|---:|---:|---:|
| **起動**（ms） | **89** | 144 | 1217 |
| **バイナリ** hello（MB、`-s -w`） | 7.7 | 6.4 | 32.4 |
| cgo | 不要 | 不要 | **必要** |
| **アイドル** CPU（%） | 0.00 | 0.03 | 2.40 |
| アイドル GPU（%） | 0.00 | 0.00 | 1.26 |
| アイドルのパッケージ電力（W） | **3.2** | 3.5 | 3.9 |
| **1 万行スクロール** fps | 60.0 | 60.0 | 53.9 |
| スクロール CPU（%） | **9.1** | 12.7 | 28.7 |
| スクロール GPU（%） | 3.1 | 3.1 | 10.8 |
| スクロール 間隔 p99（ms） | 18.2 | 18.3 | 18.2 |
| **100 個同時アニメーション** fps | 59.0 | 60.1 | 31.9 |
| アニメーション CPU（%） | **7.8** | 44.4 | 69.4 |
| アニメーション GPU（%） | 8.0 | 10.0 | 7.1 |
| アニメーション 間隔 p99（ms） | 33.3 | **18.0** | 50.6 |
| **リサイズ** 受けたサイズ / 秒 | 50 | 60 | 96 |
| リサイズ 描いたフレーム / 秒 | 55 | **120** | 6 |
| リサイズ CPU（%） | **11.2** | 18.7 | 44.1 |
| リサイズ GPU（%） | 3.6 | 6.9 | **1.7** |
| **ピークメモリ** スクロール（MB） | 240 | **159** | 434 |
| ピークメモリ リサイズ（MB） | 256 | **176** | 497 |

- CPU 使用率は 1 コアを 100% として表す。fps は画面の 60Hz で頭打ちになるので、差は CPU 使用率に表れる。
- 起動は 15 回のうち最初の 1 回だけがコールドスタートで遅いが、中央値には影響しない。
- **アニメーションの間隔 p99 が 33ms**: 8 秒間のうち 2〜6 フレームで、描画に 2 フレーム分の時間がかかっている。原因はまだ分かっていない。
- **電力**はマシン全体の値なので、同じ回における 3 者の比として読んでほしい。

### 読み方

**勝った項目**

- 100 個同時アニメーションの CPU 使用率は、Gio の約 1/6、Cogent Core の約 1/9 である。ただし Gio には影のぼかしがなく、半透明の角丸で代用している。
- 1 万行スクロールの CPU 使用率は、Gio の約 7 割、Cogent Core の約 1/3。
- リサイズの CPU 使用率は Gio の約 6 割。
- アプリのコードには目標値を書くだけで、フレームごとの計算は書いていない。

**負けた項目**（背景は [ADR 0015](ADR/0015-bench-results.md)）

- メモリ使用量はすべての項目で Gio より多い。日本語フォントの解析に約 40MB のヒープを使っている。
- リサイズ中に受け取ったサイズの数が Gio より少ない（50 対 60）。Gio は 1 つのサイズにつき 2 フレーム描くが、gowaku は 1 フレームである。原因はまだ分かっていない。

**差がなかった項目**

- アイドル時とスクロール時の GPU 使用率は Gio と同じ。起動は Gio より速く、バイナリは 1.3MB 大きい。Cogent Core はアイドル時でも CPU と GPU を使い続ける。

## 巨大なファイル

`examples/bigfile -report` でログを開き、かかった時間を同じ Windows のマシン（メモリ 16 GB）で表示しました。エディタは表示中の行だけを、別の goroutine でファイルを索引し 64 行に 1 つの見出しを持つソースから読みます（[ADR 0157](ADR/0157-editor-line-source.md)）。「最初の行の表示」は、ファイルを開いたウィンドウの最初のフレームで、`gowaku.Run` の開始から数えています。メモリは GC の後の Go のヒープで、ファイルを開いていないウィンドウの 43 MB を含みます。

| | 1 GB、1,260 万行 | 10 GB、1 億 2,500 万行 |
|---|---:|---:|
| 起動から最初の行の表示 | 76〜82 ms | 80〜84 ms |
| 全行の索引（裏で） | 0.41〜0.42 秒 | 9.1〜9.8 秒 |
| メモリ | 51 MB | 84 MB |

- 1 GB のファイルは OS のキャッシュに載っていました。10 GB のファイルは載り切らないので、索引はディスクを毎秒約 1.1 GB で読みます。最初の行の表示はそれを待ちません。
- 10 GB のファイルを書いた直後の 1 回目は、OS がまだファイルを書き出している最中で、最初の行の表示まで 678 ms かかりました。
- スクロールと検索も索引を待ちません。わかっている行まではスクロールでき、検索は別の goroutine で走り、行が増えるにつれて続きを検索します（[ADR 0154](ADR/0154-editor-background-find.md)）。

## Linux（WSL）の参考値

計測日: 2026-11-10。gowaku のみを計測した。

**GPU での数値ではない。** WSL の headless sway（Wayland、pixman）上で、Vulkan を Mesa の CPU ドライバ lavapipe で動かしている。描画を CPU で行うため、CPU 使用率は実 GPU の場合の数倍になる。ここから読み取れるのは、アイドル時に 0 になること、レイヤーが効果を発揮すること、起動時間、バイナリサイズといった傾向だけである。

手順は [results/wsl-2026-11-10.md](../examples/bench/results/wsl-2026-11-10.md) を参照。

| シナリオ | 結果 |
|---|---|
| 起動（起動から最初のフレームの後まで、7 回の中央値。最初の 1 回は 204ms） | 165ms |
| バイナリ（examples/hello、`-s -w`、linux/amd64） | 9.4MB |
| animate（100 個） | 59fps、CPU 191% |
| dense（レイヤーあり） | 59fps、CPU 102% |
| dense-flat（レイヤーなし） | 59fps、CPU 284% |
| idle | CPU 0.0%、フレーム 0 |

- scroll と resize は計測していない。ホイールとウィンドウサイズを外部から操作するハーネスが Windows にしかないためである。
- フレームレートは sway の headless 出力（60Hz）で頭打ちになる。
- dense と dense-flat の差（CPU 102% と 284%）は、Windows と macOS で確認したレイヤーの効果と同じ傾向を示している。

## macOS

計測日: 2026-11-10。同じ 3 つのプログラムを、macOS 用のハーネス（`harness/main_darwin.go`）で計測した。生データは [results/macos-2026-11-10.json](../examples/bench/results/macos-2026-11-10.json)、手順は [examples/bench](../examples/bench/README.ja.md#macos) にある。

root 権限もアクセシビリティの許可も使っていない。そのため、計測できる項目も操作の方法も Windows とは異なり、Windows の表と数値をそのまま並べて比べることはできない。違いは後述の「測れなかったもの」と「Windows との違い」にまとめた。

### 環境

| 項目 | 値 |
|---|---|
| PC | Mac（Apple M5、10 コア GPU、メモリ 24GB）、内蔵 Liquid Retina 2560×1664 / 60Hz、倍率 2 |
| OS | macOS 27.0.1 |
| Go | 1.27.3（darwin/arm64） |
| ビルド | gowaku は `CGO_ENABLED=0`。Gio と Cogent Core は `CGO_ENABLED=1`（Apple clang 21）。すべて `-s -w` |
| 比較対象 | Gio v0.10.3（Metal）、Cogent Core v0.5.27（WebGPU 経由の Metal） |
| ウィンドウ | 3 者とも 800×700 ポイント（1600×1400 ピクセル）。位置は各ライブラリの既定 |
| 回数 | 3 回の中央値。起動のみ 15 回の中央値。`caffeinate -d -i` を有効にして計測 |

計測中も他の常駐プロセス（`mediaanalysisd`、ウイルス対策の拡張機能など）が動いており、ロードアベレージは 2〜3 だった。

### 結果

太字はその行で最もよい値を示す。差が計測のばらつきの範囲内なら太字にしていない。

| 項目 | gowaku | Gio | Cogent Core |
|---|---:|---:|---:|
| **起動**（ms） | 145 | 151 | 355 |
| **バイナリ** hello（MiB、`-s -w`） | 7.5 | **5.9** | 24.4 |
| cgo | **不要** | 必要 | 必要 |
| **アイドル** CPU（%） | 0.00 | 0.00 | 2.21 |
| アイドル GPU 時間（%） | 0.00 | 0.00 | 0.26 |
| アイドルのフレーム数（60 秒） | 0 | 0 | 0 |
| **1 万行スクロール** fps | 60.0 | 60.0 | 57.6 |
| スクロール CPU（%） | **11.2** | 17.8 | 42.8 |
| スクロール GPU 時間（%） | 10.8 | **7.9** | 9.6 |
| スクロール 間隔 p99（ms） | 17.5 | 17.7 | 33.4 |
| **100 個同時アニメーション** fps | 59.0 | 60.0 | 33.2 |
| アニメーション CPU（%） | **9.0** | 32.4 | 82.4 |
| アニメーション GPU 時間（%） | 19.9 | 27.7 | **4.1** |
| アニメーション 間隔 p99（ms） | 33.2 | **18.7** | 66.8 |
| プロセスの CPU 推定電力: スクロール（mW） | **15** | 25 | 859 |
| プロセスの CPU 推定電力: アニメーション（mW） | **13** | 88 | 5462 |
| **ピークメモリ**（常駐）アイドル（MB） | 173 | **160** | 202 |
| ピークメモリ（常駐）スクロール（MB） | 175 | **169** | 272 |
| ピークフットプリント アイドル（MB） | 263 | **178** | 242 |
| ピークフットプリント スクロール（MB） | 287 | **207** | 316 |
| ピークフットプリント アニメーション（MB） | **234** | 414 | 281 |

- CPU 使用率は 1 コアを 100% として表す。fps は画面の 60Hz で頭打ちになる。
- **GPU 時間**は、GPU ドライバがプロセスごとに集計する `accumulatedGPUTime` の増分を、経過した実時間で割ったものである。Windows の「3D エンジンの使用率」とは定義が異なる。GPU の周波数によって値が変わるので、3 者の比として読んでほしい。
- **プロセスの CPU 推定電力**は、カーネルが CPU 時間に対して見積もる推定エネルギー（`ri_energy_nj`）であり、GPU やマシンの他の部分は含まない。コアの種類（P / E）や周波数によって大きく変わるため、CPU% の比とは一致しない（Cogent Core は CPU が 9 倍で、電力は 400 倍）。
- **ピークメモリ（常駐）**は `ru_maxrss` の値で、Windows のピークワーキングセットに相当する。**ピークフットプリント**はアクティビティモニタの「メモリ」欄の最大値で、Metal のバッファなど、プロセスが確保した GPU メモリも含む。
- **バイナリ**は、`examples/hello`、`hello/gio`、`hello/cogent` を darwin/arm64 向けにビルドしたときのサイズ（2^20 バイト単位）である。
- 起動は gowaku が 130〜201ms、Gio が 139〜179ms で、ほぼ同等とみなせる。

### gowaku のレイヤー（`dense`）

| シナリオ | fps | CPU（%） | GPU 時間（%） |
|---|---:|---:|---:|
| `dense`（境界あり） | 59.0 | **7.1** | 13.8 |
| `dense-flat`（境界なし） | 58.9 | 16.4 | 16.6 |

WSL（284% → 102%）と同じ傾向で効果が出ている。

### 読み方

**勝った項目**

- スクロールの CPU 使用率は、Gio の約 6 割、Cogent Core の約 1/4。
- アニメーションの CPU 使用率は、Gio の約 1/4、Cogent Core の約 1/9。GPU 時間も Gio より少ない（Gio は影のぼかしの代わりに角丸を 4 枚重ねている）。
- cgo が不要なのは gowaku だけである。macOS では Gio も cgo を必要とする。
- アイドル時は Gio と同じく 0 になる。Cogent Core は何もしていなくても CPU を 2% 使い、GPU も使い続ける。

**負けた項目**

- **メモリ使用量は Gio より多い。** 常駐メモリで 5〜15MB、フットプリントではアイドル時に 85MB、スクロール時に 80MB 多い。アイドル時のフットプリントは Cogent Core（242MB）よりも多い。Gio（414MB）より少ないのはアニメーションのときだけである。
- **スクロールの GPU 時間が Gio より多い**（10.8% 対 7.9%）。
- **アニメーションの間隔 p99 が 33ms。** 10 秒間のうち 0〜4 フレームで、描画に 2 フレーム分の時間がかかっている。Windows と同じ症状で、`dense` でも同様に起きる。原因はまだ分かっていない。
- **バイナリは Gio より 1.6MiB 大きい。**

**差がなかった項目**

- 起動時間は Gio と同等。Cogent Core は Windows（1.2 秒）より速いものの、それでも 2 倍以上かかる。

### 測れなかったもの

| 項目 | 理由 |
|---|---|
| リサイズ | 他のプロセスのウィンドウサイズを変えるには、アクセシビリティの許可が必要である。プログラム自身がサイズを変える方式にすると、Windows の「外部から `SetWindowPos`」とは別の経路になるため、実装しなかった |
| GPU 使用率（Windows と同じ定義のもの） | `powermetrics` には root 権限が必要である。代わりに GPU 時間を載せた |
| マシン全体の電力 | 同じく `powermetrics`（root 権限）が必要。代わりにプロセスの CPU 推定電力を載せた |
| 4K | 内蔵画面は 2560×1664 で、外部ディスプレイがない |
| 120Hz | 画面が 60Hz である |

### Windows との違い

- **スクロールの操作。** macOS では外部から入力を送れない（アクセシビリティの許可が必要）ので、gowaku も Gio と同様に、毎フレーム自分でリストを `ScrollSpeed` × 経過時間の位置に移動させる（`-autoscroll`、`ListController.JumpToIndex`）。Windows の gowaku はホイールの慣性でスクロールするため、描画内容が少し異なる。Cogent Core はどちらの OS でも行単位でスクロールする。
- **ウィンドウを最前面にしない。** ハーネスからはウィンドウの重なり順を変えられない。各プログラムは起動時に前面に出る。
- **ウィンドウサイズは各プログラムが決める。** gowaku と Gio は最初から 800×700 ポイントで開く。Cogent Core は内容に合わせて画面の 6 割以上の大きさで開くので、macOS でだけ、最初のフレームの後に自分で 800×700 に変更する。
- **マウスをウィンドウの外に出さない。** Windows のハーネスはウィンドウをマウスから離れた隅に移動させるが、macOS ではそれができない。マウスの位置は制御していない（アイドル時のフレーム数が 0 なので、ホバーは発生していない）。

### 計測で起きたこと

- 最初の試行（3 回分）は破棄した。その 1 回目のうち、画面がスリープしていたと思われる区間で、Gio と Cogent Core はそれぞれ 5 回起動に失敗し（最初のフレームが出ない）、同じ区間で gowaku は `scroll` と `animate` を 112〜120fps で描画していた。画面は 60Hz なので、gowaku はその間ディスプレイと同期せずに描画していたことになる。原因は、見えていないウィンドウに対して Metal が垂直同期を待たずに drawable を渡すことにあった。そこで、見えないウィンドウは最小化時と同様に描画しないよう修正した（ADR 0083 §6）。2 回目以降は `caffeinate -d -i` を有効にして計測した。
- 採用した試行でも、Cogent Core の `animate` の 1 回目は 5fps、CPU 18% だった（中央値には影響しない）。

## 目標との差

| 目標 | 結果 |
|---|---|
| 4K でリサイズしても CPU 使用率が上がらない | **未確認。** 3840×2160 は計測できていない（この PC ではウィンドウサイズの上限が 1924×1170）。そのサイズで 11.2% を使う |
| 1 万行で 120fps | 画面が 60Hz なので頭打ちになる。垂直同期なしの `examples/listview -bench` では 1800fps（Iris Xe、800×900） |
| アイドル 0% | 達成（Windows、macOS、WSL）。macOS ではリサイズを計測していないので、4K の項目は Windows の値のみ |

## 揃えられなかった点

スクロールの操作方法、Gio の影、Cogent Core のフレームの数え方、GPU の選択が、3 者の間で少しずつ異なる。詳しくは [examples/bench](../examples/bench/README.ja.md#揃えられなかった点) を参照。

電力はマシン全体の値であり、同じ条件でも 10〜18W のばらつきがあった。比較には使えないので表からは外したが、生データには残している。
