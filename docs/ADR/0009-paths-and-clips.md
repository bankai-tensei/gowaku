# 0009: パス、クリップ、スクロール、ルビ

決定日: 2026-11-07

状態: 一部を ADR 0017 で置き換え

## 背景

Phase 5 で当初の計画の残り（パス、クリップ、画像など）を実装した。計画のとおりに進まなかった点と、書かれていなかった形式を残す。

## 決定

### クリップは深度バッファ、ステンシルはパス専用

当初の計画は「角丸・パスはステンシル値のインクリメント」としていた。ところがパスの塗りもステンシルで巻き数を数える。1 バイトを分け合うと、クリップのレベルを 16 ずつ増やす操作が `INCR` でできず、D3D11 の StencilRef は比較と書き込みで同じ値なので、1 回の描画で「いまのレベルと比べて次のレベルを書く」ができない。

そこでレベルは D24S8 の深度に持たせた。

| 手順 | 深度テスト | ステンシル |
|---|---|---|
| 普通の描画（P1） | `EQUAL` z=level | 使わない |
| パスの三角形（P2） | `EQUAL` z=level | non-zero は表 `INCR` / 裏 `DECR`、even-odd は `INVERT` |
| パスの塗り（P3） | `EQUAL` z=level | `!= 0` を塗って 0 に戻す |
| クリップの押し込み | P2 の後、`GREATER` z=level+1 を書く | `!= 0` で 0 に戻す |
| クリップの解除 | `LESS` z=level を書く | 使わない |

z はシェーダーに渡さない。どの頂点も z=0 を出力し、ビューポートの `MinDepth = MaxDepth = level/256` で深度が決まる。`gpu.Instance` も全シェーダーも変えずに済み、Vulkan にも同じ仕組みがある。

押し込みで外側のクリップの外まで広がらないのは、P2 が親のレベルと `EQUAL` で判定するから。解除は被覆矩形の範囲で「今より深いものを 1 段戻す」ので、外側のクリップの外には触らない。

角丸クリップも `Path` に変換してこの経路を通る。SDF で `discard` する案は、MSAA のサンプルごとの被覆が得られず縁がギザギザになるのでやめた。

### フレーム全体を MSAA で描く

**ADR 0017 で変更した。** いまは要るフレームだけ MSAA で描く。

パスだけを別のターゲットに描くと合成の順序が崩れる。Surface は 4x の色と深度を持ち、`EndFrame` で resolve する。

| 計測（Iris Xe、1800×1020） | MSAA なし | 4x |
|---|---|---|
| 1 万矩形 | 約 1000fps | 約 1000fps（ばらつきの範囲） |
| 1 万矩形すべてに影 | 131fps | 117fps |

当初の計画にあった Intel ドライバ対策として `d3d11.Options.Samples = 1` で切れる。

### 小さいパスはアトラス、それ以外はステンシル

物理 64px 以下で、単色の塗りで non-zero のパスは `x/image/vector` でラスタしてアトラスに載せる（当初の計画）。even-odd は `x/image/vector` に無いのでステンシルに回す。キーは `*paint.Path` なので、描いたパスは変えない約束にした。

ストロークは太さを持つ三角形の集まりで、向きをそろえて non-zero の和集合にする。角と端はすべて丸。

### `Ticker` と `SpringSimulation` を Phase 6 から前倒しした

当初の計画は Phase 5 の項目に「スプリング慣性」を置きつつ、部品を Phase 6 の `motion` に置いていた。`core.Ticker` と `motion.SpringSimulation` だけ先に入れた。Ticker が走っている間だけループが待たずに回り、`Present` の vsync がペースを作る。止まれば再びイベント待ちになる。

スプリングの開始時刻は次の tick で確定する。ホイールは時計を持たないフレームの間に来るので、前回の tick の時刻を使うと、しばらく止まっていた後の 1 回目が一瞬で飛ぶ。

### ホイールの慣性は目標を動かす方式

ホイールは目標位置を動かし、臨界減衰のスプリングが速度を保ったまま追う。端の先 60px まで目標を許し、そこから端へ戻すのが端のバウンス。デスクトップなので、マウスのドラッグによるスクロールは入れていない。

### ListView は行の高さが固定

State が見える範囲を計算し、範囲が変わったときだけ再ビルドする。スクロールの 1 フレームは `SetOffset` だけ。可変高さには実測の積み上げが要るので v2 候補。高さが分かるのは Layout の後なので、`Tree.NeedsBuild` を見てフレームの中で Build と Layout をやり直し、最初のフレームから行が見える。

### ルビ

`Span.Ruby` を持つスパンは 1 つのクラスタになり、行で割れない。モノルビはスパンを分けて書く。

- 大きさは親文字の半分（JLReq 3.3.2）。
- ルビが短ければ 1:2:1 で配置（JLReq の肩付き・中付きのうち中付き）。
- ルビが長ければ隣のかなに 1 字分まで掛け、足りなければ親文字を 1:2:1 で開く。
- ルビのある段落は行送りの係数を 1.75 以上にする。行ごとに変えない。

行頭・行末で掛けた分が版面からはみ出す場合の調整は入れていない。

## 含めなかったもの

- 画像のミップマップ。大きな画像を強く縮小すると荒れる。
- ListView の可変高さ、ScrollBar（Phase 6）、キーボードスクロール、ドラッグスクロール。
- `Canvas.Transform`（Phase 6）。

## 結果

- 全シェーダーの入力は変わらず、インスタンスは 112 バイトのまま。
- ポップ後に描いたものが正しいことまで、実 GPU のピクセルテストで確認した。
- リソース解放の検査（`TestSurface_ReleasesEveryReference`）が MSAA ターゲットの参照漏れを見つけた。
