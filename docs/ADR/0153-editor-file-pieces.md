# 0153: Editor でファイルを読み込まずに開き、編集して保存する

決定日: 2026-11-17

状態: 一部を ADR 0157 で置き換え（ファイルの読み書きはアプリの側に移した）

## 背景

`editor.Controller` は本文を行の文字列の配列で持ち（ADR 0061）、`SetText(string)` で全文を受け取る。443 MB、500 万行のログでは、読み込み 1.07 秒、string への変換 0.22 秒、`SetText` 0.43 秒で、最初のフレームまで 1.88 秒かかり、ヒープは 563 MB 増えた。数 GB のファイルは、メモリに載せることもできない。

閲覧だけでなく編集もしたい、ただしファイル全体は読み込まず、検索や選択の近くだけを読み、保存するときに残りを読みながら書き出す形にしたい、というのが持ち主の要望だった。

## 選択肢

- **A. 読み取り専用の行のソース。** 行の数と i 行目を返すものを Editor に渡す。仕組みは小さいが、編集できない。
- **B. ファイルの上のピーステーブル。** 文書を「ファイルの何行目から何行」と「メモリにある行」のピースの並びで表す。ファイルの行は見えるときに読み、編集した行だけをメモリに持ち、保存はピースを順に新しいファイルへ書き出す。
- **C. 全体をメモリに載せたままの別の構造（ロープなど）。** メモリの問題が解けない。

## 決定

案 B。

### 文書（`lineBuffer`）

- ピースは、ファイルの行の範囲（`file`、`start`、`n`）か、メモリの行（`lines`）のどちらか。各ピースは「行の長さ＋改行の 1」の合計（`bytes`）を持ち、文書の長さはその総和から 1 引いたもの。ピースごとの行数とバイト数の累積を持ち、行もオフセットも二分探索で引く。
- `SetText` の文書は、メモリのピース 1 つ。これまでの行の配列と同じで、どの編集も 1 つのピースの中で済む（速い経路）。既存のテストは期待値を変えずに全部通り、ベンチマークも変わらない。
- 複数のピースにまたがる編集は、両端のピースを切り、間を新しいメモリのピースにする。隣り合うメモリのピースは 1 つにまとめるので、ファイルの行を 1 行ずつ打ち直しても、ピースは増え続けない（300 回のランダムな編集のテストで確かめた）。
- 元に戻す（`kit.History`）は文書全体のバイト位置で動くので、そのまま使える。

### ファイル（`fileSource`）

- 64 行ごとに、その行がファイルの中と文書の中で始まる位置を持つ。1 億行で 25 MB。行は 64 行の塊ごとに `ReadAt` で読み、`\n` で切る。読んだ塊は 2 世代のキャッシュ（合わせて 512 塊）に持つ。
- mmap は使わなかった。標準ライブラリに無く、外でファイルが縮むとプロセスが落ちる。`ReadAt` なら、そのときは読めない行になるだけで済む。
- 改行は `\n` と `\r\n` を区切りとし、`\r\n` は文書の中では `\n` の 1 バイトとして数える。`SetText` と違い、単独の `\r` は区切りにせず、行の中の文字として残す。区切りにすると、索引を作るときに `\n` だけを探す速い走査ができないため。
- `OpenFile` は先頭の 1 MB（または最初の 1 行が終わるまで）を索引してから返り、残りは別の goroutine で索引する。見つかった分は `fileSource.pending` に渡し、Editor の State の `Poster`（ADR 0152）で UI の goroutine に知らせる。UI の goroutine は、それを文書の末尾に足す（`grow`）。Editor から見ると、最後の行が編集されたのと同じ変更なので、表示の仕組みをそのまま使える。利用者の編集ではないので、`OnChange` は呼ばない。索引の途中でも、読み終わった行は編集できる。
- 折り返さないときは、行ごとの段数の表（`rowTable`）を持たず、行の数だけを持つ。1 億行で 900 MB かかっていたものが 0 になり、行が増える編集で表を作り直すこともなくなった。

### 保存

- `SaveAs(path)` は、同じフォルダーの一時ファイルにピースを順に書き出し、`Sync` してから元のファイルと差し替える。ファイルのピースはファイルの中のバイトをそのまま写すので、元の改行（`\r\n` か `\n`）が残る。メモリの行は、ファイルの最初の行の改行で書く。
- 書きながら、書いたバイトを索引にかけるので、保存の後は読み直さずに新しいファイルの索引ができている。文書は新しいファイルの 1 つのピースになり、元に戻す履歴、選択、スクロールはそのまま残る。
- Windows では開いているファイルを置き換えられないので、差し替えの前に元のファイルを閉じる。差し替えに失敗したら、元のファイルを開き直す。
- 索引の途中では保存できない（`ErrLoading`）。`SetText` の文書の `Save` は `ErrNoFile` を返し、`SaveAs` するとそのファイルの文書になる。

### API

`Controller.OpenFile(path, onLoad)`、`Save`、`SaveAs`、`Close`、`Loading`、`LoadErr`、`FilePath`、`ErrLoading`、`ErrNoFile`。

## 結果

- 443 MB、500 万行のログ（OS のキャッシュに載った状態）: 最初のフレームまで 1.88 秒から 24 ms、全部の行の索引まで 0.15 秒（裏で）、ヒープの増加は 563 MB から 2 MB。真ん中の行の編集は 3 ms で、ピースは 3 つ。保存は 0.49 秒。
- テスト（`widgets/editor/editor_file_test.go`）: 小さなファイルの改行の扱い、索引を小さく区切って何度にも分けて読む、読み込み中と読み終わった後のランダムな編集を文字列と比べる（行、長さ、オフセット、位置）、保存で元の改行が残り新しい行はファイルの改行になる、ファイルの両端の編集の保存、保存の後に元に戻して保存し直す、保存の後に一時ファイルが残らない、Editor に表示したまま索引が進む。race 検出器あり。
- 残り:
  - 検索は、まだ UI の goroutine で文書全体を読む。裏で検索して少しずつ出す形にする（次の ADR）。
  - `SaveAs` は書き終わるまで UI を止める。
  - `Text`、全選択してのコピー、全体を削除して元に戻すことは、ファイル全体を文字列にする。
  - 1 行が巨大なファイル（数百 MB の 1 行の JSON など）は、その 1 行を丸ごと読んでレイアウトする。
  - 開いている間に外でファイルが変わると、行がずれる。気づく仕組みは無い。
  - 折り返すと、行ごとの段数の表を持ち、行を見積もるために全部の行を読む。
