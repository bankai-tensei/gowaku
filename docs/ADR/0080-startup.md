# 0080: 起動を短くする

決定日: 2026-11-10

状態: 採用

## 背景

当初の計画の性能項目「起動短縮」を、ヒアリングで作ることにした。

この PC（i7-12700H、D3D11）で、プロセスの起動から最初のフレームまでを測った。

| | 時間 |
|---|---|
| examples/hello | 約 142ms |
| examples/gallery | 約 275ms |

hello の時間の行き先:

| 処理 | 時間 |
|---|---|
| D3D11 のアダプタ | 約 15ms（フォントと並行していた） |
| D3D11 のデバイス | 約 32ms（フォントと並行していた） |
| `fontscan.UseSystemFonts` | 約 50ms。ほぼ全部が約 1130 ファイルの `os.Stat`。Windows は `C:\WINDOWS\Fonts` と `C:\Windows\Fonts` を別の 2 つとして返すので、同じフォルダを 2 回なめている。go-text の中なので、フォークしないと直せない |
| Yu Gothic の解析 | 約 55〜68ms（索引の後に直列で） |
| CreateWindow | 約 37ms。うち ShowWindow が約 20ms、OLE のドロップ登録が約 6ms（フォントの後に直列で） |
| サーフェス | 約 7ms |
| 最初のフレーム | 約 8ms |

gallery では、最初のフレームでさらに Yu Gothic の B と M を読み込み、レイアウトで約 107ms かかっていた。

## 決定

### 1. ウィンドウとデバイスを、フォントと並行して開く

- `Run` はデバイスの作成（`createDevice`）をゴルーチンで始める。その間に UI ゴルーチンは、プラットフォームを開いてウィンドウを作る。
  - `openPlaced` から `nativeOptions` を分けた。`attach` は用意したウィンドウを受け取る。
- デバイスが届いたら、`start` がサーフェスを作る。
- テーマの Canvas（または `App.Background`）で 1 フレーム present する。これで、ウィンドウに OS のごみが見えない。最初の present の費用も、待ちの経路から外れる。
- それからフォントを待ち、`runWith` に入る。テスト用の `run(p, b, shaper, a)` は変えていない。
- 失敗の経路では、ウィンドウを閉じ、サーフェスとデバイスを壊す。Linux も同じ形で、Vulkan を使う。
- **副作用**: 最初のフレームまで、ウィンドウがテーマの地の色で約 40ms 見えるようになった（前は約 13ms）。

### 2. 前回の最初のフレームのフォントを先に読む

- 最初のフレームの後に、app が新しい公開 API `Shaper.SaveStartupFaces()` を呼ぶ。
  - 読み込んだ顔の fontscan の Location を、ファイルの大きさと更新時刻と一緒に、`<UserCacheDir>/gowaku/startup_faces_v1_<実行ファイル名>.txt` に書く。一覧が変わったときだけ書く。
  - 実行ファイルごとに分けたのは、アプリどうしで一覧を奪い合わないため。`go run` でも名前が変わらない。
- 次の `NewSystemShaper` は、`UseSystemFonts` が走っている間に、それらのファイルを 1 つずつゴルーチンで解析する。それから `FontMap.AddFace` に、システムの索引と同じ Location、ファミリ、アスペクトで足す。
  - fontscan の `faceCache` は Location で引くので、解決すると同じ顔が返り、ファイルを読み直さない。
  - 一覧の順に足すので、fontscan の最後の手段 `firstFace` も変わらない。
- 中身が変わったファイルや、もうシステムの索引に無いファイルは飛ばす。フォントを渡して作った Shaper（テストのすべて）は、一覧を見ない。
- 結果: hello のフォントの準備が約 110ms から約 60ms に縮んだ。gallery の、最初のフレームでのフォントの読み込みは無くなった。

### 3. 採らなかったもの

| 案 | 理由 |
|---|---|
| 起動中の GOGC の調整 | 2〜5ms しか変わらない |
| a11y のブリッジを後回しにする | もともと 0ms |
| OLE のドロップ登録を後回しにする | 約 6ms。ウィンドウの経路はもう待ちの経路ではない |
| fontscan の索引を自前のものに置き換える | 足跡を差し込む公開 API が無い |
| 予備のフォントを遅れて読む | fontscan がもうそうしている |
| シェーダーのキャッシュ | D3D11 は、もうコンパイル済みのバイトコードを使っている |
| 最初のフレームを Yu Gothic だけで描き、後でシステムの索引に替える | フォントの解決が変わり、レイアウトのやり直しが要る |

## 結果

起動から最初の pump の後までを、9 回の中央値で、前のバイナリと交互に 2 組測った。

| | 前 | 後 |
|---|---|---|
| examples/hello | 141.6 / 144.7ms | 78.8 / 79.9ms |
| examples/gallery | 271.8 / 277.9ms | 131.5 / 139.6ms |

- 新しい exe の最初の 1 回は約 1 秒かかる（新しいバイナリを Defender が調べている）。中央値には入れていない。
- Vulkan（Windows で一時的に Run を切り替えて測った）は 780ms から 758ms で、悪くなっていない。時間のほとんどはインスタンスの作成（約 700ms）。

## 残したこと

- `fontscan.UseSystemFonts` の 2 回なめは go-text の中にある。上流に報告する候補。
- ベンチ（examples/bench）の startup の行は、16c の測り直しで更新する。
