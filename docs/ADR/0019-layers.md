# 0019: レイヤーキャッシュ、部分 present はやめる

決定日: 2026-11-08

状態: 採用

## 背景

当初の計画の Phase 9。`RepaintBoundary` の下を自前のテクスチャに描き、変わらなければ描き直さない。第 2 段階の部分 present は、計画の判断点で続けるかを決める。

## 決定

### 記録

- `paint.Layer` は自分の原点を基準に記録した DisplayList。記録のたびに版が上がる。親のリストには `OpLayer` が 1 個入る。
- `core.RenderRepaintBoundary` が `Layer` を持つ。`MarkNeedsPaint` は最も近い境界まで登り、そこで止まる。境界が無ければルートに届く。
- `Tree.Repaint` は、ルートが汚れていなければ親のリストをそのまま残し、汚れた境界だけ記録し直す。
- 位置の変更（`SetOffset`）は親の絵の変更として扱う。スクロールは親を記録し直すが、行は記録し直さない。
- 登る処理は塗りの世代番号で打ち切る。同じ世代の 2 回目は 1ns で返る。

### レイヤーで描けない場合は直接描く

| 場面 | 振る舞い | 理由 |
|---|---|---|
| 親に scale か opacity がかかっている | 記録の時点で直接描く（`Canvas.CanDrawLayer`） | 仕上がったピクセルは拡大に追従しない。まとめて薄めると命令ごとの opacity と結果が変わり、既定の見た目が変わる（当初の計画の互換方針） |
| 境界の入れ子 | 内側は外側に溶ける | レイヤーの描画中に別のレイヤーを読むと、同じページへの読み書きになりうる |
| パスや形のあるクリップを含む | フレームに命令として混ぜる（インライン） | ページは 1 サンプル。MSAA の部分 resolve は D3D11 に無い |
| 2048px を超える | インライン | ページに入らない |
| 256MB のページがすべて今のフレームで使用中 | インライン | 当初の計画のリスク対策 |
| 3 フレーム以内に続けて変わった | 落ち着くまでインライン | 下を参照 |

インラインの経路があるので、どの場合も絵は同じになる。

### 連続で変わるレイヤーはページに載せない

最初の実装はリサイズで v1 より重かった（CPU 15.9% → 19.4%、ピークメモリ 231MB → 303MB）。幅が変わるたびに全行を描き直して、さらに合成していたため。続けて変わるレイヤーは保存しても再利用されないので、落ち着くまでフレームに混ぜる。これで v1 と同等に戻った。

### ページ

- 2048² の RGBA8。棚（高さ 8px 単位）に詰める。解放は 1 枚単位で、断片化を扱わない。
- 既存のページが埋まったら、2 フレーム以上使われていないページを新しいページより先に再利用する。最初の実装はスクロールで上限の 256MB まで埋まった（ピーク 438MB）。これで 212MB に下がった。
- 合成は `InstanceImage` のまま。シェーダーは 1 行も変えていない。
- ピクセルは物理ピクセルに揃えて置く（`snapOrigin`）。行の中の部品は行に対して固定で丸めるので、端数のスクロール位置で直接描いたときと 1px 違う場所がありうる。

### バックエンド

`gpu.Backend` に `CreateTarget` と `DrawToTarget`、`gpu.Batch` に `Clears` を足した。

- D3D11: 深度なしで描く。部分クリアは `ID3D11DeviceContext1::ClearView`。
- Vulkan: 平の render pass と互換の pass を別に持ち、同じパイプラインを使う。互換には依存も同じである必要があるので、サンプリングとの行き来はイメージバリアで行う。部分クリアは `vkCmdClearAttachments`。ビューポートの定数が違うので、フレームごとに定数バッファをもう 1 組持つ。

### 部分 present はやめる

当初の計画は「差が 10% 未満なら止める」とした。D3D11 に `Present1` の `DirtyRects`（`FLIP_SEQUENTIAL` が必要）を実装して測り、外した。

| `dense`（Iris Xe、60Hz、4 回） | 全画面 present | 部分 present |
|---|---|---|
| プロセスの CPU（%） | 5.9 | 7.6 |
| プロセスの GPU（%） | 6.3 | 6.5 |
| 全プロセスの 3D GPU（%、4 回の平均） | 14.0 | 16.6 |

変わるのが 64px の箱だけという、部分 present に最も有利な条件でも改善が無い。全プロセスの値は他のプロセスを含むので揺れが大きいが、悪化の側にある。スクロールとリサイズは画面全体が変わるので、そもそも差が出ない。

`dwm.exe` の CPU は権限が無く読めなかった。4K でも測っていない（この PC の上限は 1924×1170）。4K や別の GPU で結果が変わる可能性はあるが、再開する根拠も今は無い。`VK_KHR_incremental_present` は実装していない。

## 結果

Iris Xe、60Hz、1200×1050、各 3 回の中央値。同じ時間帯に交互に測った。

| シナリオ | 値 | v1 | v2 |
|---|---|---:|---:|
| `dense`（境界なし → あり） | CPU（%） | 12.5 | **5.8** |
| | ピークメモリ（MB） | 121 | 141 |
| `scroll` | CPU（%） | 8.8 | 8.0 |
| | GPU（%） | 4.8 | 5.2 |
| | ピークメモリ（MB） | 175 | 212 |
| `animate` | CPU（%） | 7.7 | 6.4 |
| `resize` | CPU（%） | 20.9 | 18.8 |
| | ピークメモリ（MB） | 220 | 262 |

- **効くのは「大きな静止部分の近くで小さなものが動く」画面。** CPU が半分以下になる。
- **`ListView` の行の境界は、この行の内容では CPU の差がばらつきの範囲に収まる。** 再ラスタは可視行だけになったが、1 万行スクロールのコストの大半は Present の経路で、もともと行の描画ではない。代わりにメモリが増える。レビューで既定のまま残すと決めた（2026-11-08）。行の中身が重いアプリでは再ラスタの節約が効くため。
- `animate` の `p99` は v2 だけ 33ms に見える。これは計測の都合。v2 は変化の無いフレームで親を塗らないので、`Paint` で数えるプローブが抜ける（240 フレーム中 6 回）。実際の描画回数は 240 で、落ちていない。

## 検討してやめたこと

- レイヤーごとに 1 テクスチャ: 当初の計画どおり行で破綻する。
- まとめて薄めるレイヤーの opacity: 見た目が v1 から変わるのでやめた。`Opacity` の下は直接描く。
- 自動で境界を置く: 当初の計画どおり明示だけ。
