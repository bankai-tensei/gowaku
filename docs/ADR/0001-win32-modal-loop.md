# 0001: Win32 のモーダルループ中は同一スレッドのコールバックで描く

決定日: 2026-11-07

状態: 採用

## 背景

当初の計画のイベントループは `WaitEvent` が戻ってくることを前提にしている。ところが Win32 では、ウィンドウの枠をドラッグすると `DefWindowProc` が内部でモーダルなメッセージループに入り、マウスを離すまで戻らない。システムメニューを開いたときも同じ。その間 `WaitEvent` は `DispatchMessageW` の中で止まるので、何もしないとリサイズ中に画面が更新されず、アニメーションも止まる。

## 選択肢

1. **メッセージポンプを別スレッドに置く。** UI ゴルーチンは止まらない。ただし当初の設計の決まり「UI はメインゴルーチン専用」を崩し、ウィンドウ所有スレッドと描画スレッドの間に同期が要る。DXGI はメッセージポンプのスレッドが描画を待つとデッドロックし得る。
2. **モーダル中に WndProc から同じスレッドでコールバックを呼ぶ。** スレッドは 1 本のまま。
3. **何もしない。** リサイズ中は固まる。軸 1 の「リサイズしても CPU が上がらない」のベンチが成り立たない。

## 決定

選択肢 2。`Platform.SetModalHandler(fn)` を追加する。

- `WM_ENTERSIZEMOVE` / `WM_ENTERMENULOOP` から対応する EXIT までを「モーダル中」とする。
- モーダル中は `WM_SIZE`、`WM_PAINT`、`WM_DPICHANGED`、`WM_CLOSE`、ウェイクアップの各メッセージの処理後に `fn` を呼ぶ。
- マウスが止まっていてもアニメーションが続くように、モーダル中だけ 16ms の `WM_TIMER` を動かして `fn` を呼ぶ。
- `fn` の中の `WaitEvent(0)` はキューを読むだけで、メッセージを汲み上げない。OS のループの内側で汲み上げると順序が崩れる。
- `fn` の再入は拒否する。`ResizeBuffers` や `Present` はウィンドウにメッセージを送ることがあるため。そのメッセージのイベントはキューで待つ。

`Wake` はスレッドメッセージではなくメッセージ専用ウィンドウへ `PostMessageW` する。スレッドメッセージはモーダルループが捨ててしまう。

## 結果

- アプリ側はメインループの本体を 1 つの関数にし、`WaitEvent` の後と `fn` の両方から呼べばよい。`examples/triangle` の `pump` がその形。Phase 2 で `gowaku.Run` の中に隠れるので、ライブラリ利用者には見えない。
- `Build` や `Layout` が OS の呼び出しの内側で走ることになる。panic は Win32 のスタックフレームをまたいで伝播できないのでプロセスが落ちるが、ライブラリ内で `recover` しない方針（CODING_STYLE §6）と矛盾はしない。
- X11 にはモーダルループが無いので、`platform/x11` の `SetModalHandler` は何もしない実装でよい。
