# 0151: Table の行を RowCount と Row で渡す

決定日: 2026-11-17

状態: 採用

## 背景

`collection.Table[T]` は行を `Rows []T` で受け取る（ADR 0058）。表は見えている行しか描かないので、100 万行でも 1 フレームは数 µs で済む。しかし、行がアプリのデータ構造の中に別の形である場合、たとえば巨大なログや CSV の行を、ファイルの中の位置の索引で持っている場合には、表に渡すためだけに `[]T` を作らなければならない。ADR 0058 は「並び順のスライスを渡して `Table[int]` にする」形を勧めていたが、それでも 1 行に 8 バイトかかり、1 億行で 800 MB になる（ADR 0150 の調査で、`Rows []int` の 1 億行でヒープが 857 MB 増えた）。

## 選択肢

- **A. `RowCount int` と `Row func(i int) T` を足す。** 型はこれまでの `Table[T]` のまま。列の関数（`Text func(T) string` など）も変わらない。`Row` があれば `Rows` の代わりに使う。
- **B. `TableSource[T]` インターフェース（`Len()`、`At(i)`）を受ける。** データ構造の型をそのまま渡せるが、関数 2 つで足りるものに型を 1 つ足すことになる。ほかの部品（`List.ItemCount` と `ItemBuilder`、`GridView`）は数と関数で受けていて、それと揃わない。
- **C. 別の部品（`VirtualTable[T]` など）にする。** 同じ機能の部品が 2 つになり、列、選択、編集、絞り込みの説明も 2 か所に要る。

## 決定

案 A。

- `Row` が nil でなければ、表は `RowCount` 行あり、i 行目は `Row(i)` である。`Rows` は読まない。両方を与えた場合も `Row` が勝つ（テストあり）。
- コールバックの添字（`OnActivate`、`OnContextMenu`、`OnCheck`、`TableController` の選択など）は、`Rows[i]` と同じく `Row(i)` の i を指す。
- 表が `Row` を呼ぶのは、レイアウト、描画、Semantics で扱う行と、選択中の行（`RowKey` の照合）だけである。見えている行は 1 フレームに何度か呼ばれるので、`Row` は行を作るのではなく引くもの（データへの添字、表示の近くの行のキャッシュ）にするよう godoc に書いた。
- 中では `dataTableState.at(i)` が `Rows[i]` か `Row(i)` を返し、行の数は `count` に持つ。`tableCore` は行の数しか知らないので、変更はこの型の中だけで済んだ。

## 結果

- テスト（`widgets/collection/datatable_rowsource_test.go`）:
  - 1 億行を `Row` で渡しても、ヒープの増加は 16 MB 未満。最初のフレームと、途中へのスクロールで `Row` を呼ぶのは 200 回以下。スクリーンリーダーには 1 億 1 行（見出しを含む）と伝わり、Ctrl+End で最後の行に届き、その行の名前は `Row` から作られる。
  - `Rows` と `Row` の両方を与えると `Row` が読まれる。
  - `Row` が読む順を変えて並べ替えても、`RowKey` で選択が同じ行に残る。
- カタログの Table の説明に `RowCount` と `Row` を足した。
- 残り:
  - `RowKey` を与えると、行が変わったときに選択を探し直すため、全行の `RowKey` を 1 度ずつ呼ぶ（ADR 0127）。1 億行では `Row` も 1 億回呼ばれる。巨大な表では、選択を添字のまま持つ（`RowKey` を与えない）か、選択を自分で付け直す。
