# 0034: ListView の行の高さを、前もって分かる関数で行ごとに変える

決定日: 2026-11-08

状態: 採用。表の上端の型は ADR 0150 で float64 に変えた

## 背景

音楽プレーヤーの見本アプリで、表の見出し行、アルバムの区切り行、曲の行を 1 本の `ListView` に並べたかった。ところが `ListView` は全行が同じ高さ（`ItemExtent`）しか持てず、`TODO(v2): rows of different heights` が残っていた。見出しはリストの外に出すしかなく、区切り行は曲の行と同じ高さにするしかなかった。

満たしたいこと:

- 仮想化を保つ。1 万行でも、作るのは見えている行と前後 3 行（`cachedItems`）だけ。
- スクロール中（tick、行の範囲の判定、Layout、Paint）はアロケーションしない。
- 今の `ItemExtent` の API と挙動、ゼロ値（48）をそのまま残す。固定の高さの速い道も残す。
- 慣性スクロール、スクロールバー、上限の無い長さでの panic（0026）がそのまま動く。

## 選択肢

### (a) 高さを返す関数を前もって受け取り、行の上端の累積和の表を持つ

- `ItemExtentOf func(i int) float32` を足す。nil なら今までどおり `ItemExtent`。
- 全行の上端を累積和で表（`[]float32`、行数 + 1 個）に入れる。オフセットから行を引くのは二分探索で O(log n)、行の位置は表を引くだけで O(1)。
- 全体の高さが最初から正確に分かるので、スクロールバーのつまみの大きさも位置も跳ねない。端までのスクロールの上限も正確。
- 費用は 1 行 4 バイトと、表を作り直すときの O(n) の関数呼び出し。

### (b) 行を測って、まだ測っていない行は見積もる（Flutter の `SliverList`）

- 高さを知らなくてよいので、文章の折り返しで高さが決まる行にも使える。
- ただし見積もりと実測が違うたびにスクロール位置を補正する必要があり、スクロールバーのつまみも跳ねる。末尾への移動やスクロールバーのドラッグで、まだ測っていない行を飛び越えると位置が定まらない。
- 測った高さのキャッシュの寿命（データが変わったとき、幅が変わったとき）を管理する仕組みも要る。当初の計画の「`ListView` の高さキャッシュと高さ不定時の高速ジャンプ」がこれに当たり、v1 の範囲を超える。

### (a) の細部

**表をいつ作り直すか。** 関数は比べられないので、「同じ関数か」は判定できない。行数が同じでもデータが変われば高さは変わりうる（同じクロージャが新しいスライスを読む、など）。

- (a-1) 行数が変わったときだけ作り直す。
  - 安いが、行数が同じまま高さが変わると古い表のままになる。
  - 気付きにくい不具合になる。
- (a-2) 親の再ビルドで新しい `ListView` の値が来たとき（`DidUpdateWidget`）に作り直す。
  - スクロールによる自分の `SetState` では作り直さない。
  - 1 万行で数十マイクロ秒で、表のメモリは使い回すのでアロケーションもしない。
- (a-3) 利用者に版番号のフィールドを持たせる。
  - 速いが、フィールドが増え、更新を忘れると (a-1) と同じ不具合になる。

**(a-2) を採る。** 高さを変えるには親がデータを変えて再ビルドするはずなので、その時に読み直せば必ず正しい。スクロール中は関数を呼ばない。

**誤差。** 累積和は float64 で足し、各行の上端を 1 回だけ float32 に丸める。float32 で足し続けると、100 万行でずれが数千ピクセルになる。

## 決定

**(a) と (a-2) を採る。**

- `layout.ExtentTable` に表を置く。`Reset(n, extent)`、`Offset(i)`、`Extent(i)`、`IndexAt(y)`、`Total()`、`Version()` を持つ。メモリは `Reset` のたびに使い回す。
- `layout.RenderList` に `Extents *ExtentTable` を足す。
  - nil なら今までどおり `Extent` で置く。
  - nil でなければ、行 k を `Offset(First+k)` に置き、高さ `Extent(First+k)` のきつい制約で並べる。
  - `SetExtents` は、表の差し替えか `Version` の変化を見て、そのときだけ Layout をやり直す。
- `widgets.ListView` に `ItemExtentOf` を足す。
  - 状態（`listState`）が表を持つ。
  - `DidUpdateWidget` で古いとし、次に使うときに作り直す。
  - 見える範囲は `IndexAt(top) - cachedItems` から `IndexAt(top+view) + 1 + cachedItems` まで。スクロールバーの中身の高さは `Total()`。
- 高さ 0 の行は隠れた行として許す。負と NaN は `panic("gowaku: ListView.ItemExtentOf returned a negative or NaN height")`。

`ItemExtentOf` が nil のときは表を作らず、コードの道も今までと同じ。

## 影響

- 見出し行・区切り行・普通の行を 1 本の `ListView` に混ぜられる。見本アプリ は見出しをリストの中に戻せる。
- 1 万行で高さの違うリストのスクロールは、行の範囲が変わらないフレームで allocs/op = 0（`BenchmarkListView_VaryingScrollFrame_10k`）。
  - 行が入れ替わるフレームで行のウィジェットを作るとアロケーションするのは、固定の高さの道と同じ。
- 高さが中身で決まる行（折り返す文章など）はまだ扱えない。必要になったら (b) を、この表を見積もりで埋める形で足す。
- 親が毎フレーム再ビルドする場所に置くと、毎フレーム O(n) で関数を呼ぶ。doc に「安く保つこと」と書いた。
- 行の高さが変わってもスクロール位置（ピクセル）はそのまま保ち、末尾を越えたら末尾に寄せる。見えている行を基準に位置を保つ処理はしていない。
