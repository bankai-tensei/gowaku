# 0154: 大きな文書の検索を裏で走らせ、見つかった分から出す

決定日: 2026-11-17

状態: 採用

## 背景

`editor.Controller.Find` は、文書全体を UI の goroutine で検索してから返っていた（ADR 0061）。500 万行、443 MB のログでは、大文字小文字を区別しない検索が 0.44 秒（ADR 0150 の後の修正で 2.8 秒から縮めた）、大文字小文字を区別しない正規表現は 11〜50 秒かかり、その間 UI が止まった。`OpenFile`（ADR 0153）のファイルでは、検索がファイル全体を UI の goroutine で読むことにもなる。

持ち主の判断は「裏で検索して、少しずつ出す」だった。

## 選択肢

- **A. 検索を別の goroutine で走らせ、結果を少しずつ渡す。** どれだけ遅い検索でも UI は止まらない。
- **B. 検索そのものを速くする。** 正規表現から必ず含まれる文字列を取り出して先に絞り込むなど。止まる時間は縮むが、ゼロにはならない。
- **C. そのまま。**

編集が検索の途中に入ったときの扱いも決める必要があった。

- **編集のたびに検索をやり直す。** 単純だが、数 GB のファイルで 1 文字打つたびにファイル全体を読み直すことになる。
- **検索は始めたときの文書の写しの上で続け、その間の編集を記録して、結果の行番号を編集に通して直す。** 編集された行の結果は捨てる。編集された行は、これまでどおり UI の goroutine がその場で検索し直しているので、抜けも重なりも出ない。

## 決定

案 A。編集は記録して結果を直す。

- **どの文書を裏で検索するか:** `OpenFile` のファイルと、4 MB を超える文書。それ以外はこれまでどおり UI の goroutine で検索し、`Find` はすぐに全部の件数を返す。既存のテストはそのまま通る。
- **写し:** 検索を始めるときに、ピースの並びを区間（`findSeg`）の列にする。メモリのピースは行の文字列のスライスを写す（文字列そのものは不変なので写さない）。ファイルのピースは、ファイルの中のバイトの範囲にして、検索の goroutine が自分で `ReadAt` で 1 MB ずつ読む。行のキャッシュ（ADR 0153）は UI の goroutine のものなので触らない。
- **結果の渡し方:** 6 万 5 千行ごとに、見つかった分を `findJob.pending` に渡し、Editor の State の `Poster`（ADR 0152）で UI の goroutine に知らせる。結果は、その区間を列に入れたときの行番号で付いてくる。UI の goroutine は、そのとき以降の編集の記録（`finder.log`）に通して行番号を直し（`moveThrough`）、並びを保って今の一致に混ぜる（`merge`）。
- **ファイルが読み込み中のとき:** 索引が進んで文書の末尾に行が足されると、その行の区間を検索の列に足す。検索が終わっていれば、その区間だけの検索を始める。
- **やめるとき:** 新しい `Find`、検索を閉じる、`SetText`、`OpenFile`、`Close` で、走っている検索に止まるよう知らせ、その結果は捨てる。`SaveAs` は検索中ならいったん止め、保存の後に新しいファイルで検索し直す。一致が 10 万件に達したら止める（これまでと同じ上限）。
- **API:** `Find` は裏で検索するときは 0 を返し、`Searching()` が真の間、`Matches` は見つかった分だけを持つ。`ReplaceAll` は見つかった分だけを置き換え、検索をやり直す。
- **検索バー:** 検索中でまだ一致が無いときは「検索中…」（`basic.Strings.Searching`、英語は "Searching…"）、一致があれば件数の後に「…」を付ける。結果が届くたびに件数を出し直す。

## 結果

- 500 万行、443 MB のファイル: `Find` はすぐに返り、検索の間のいちばん長いフレームは 8 ms。大文字小文字を区別しない検索は 0.73 秒、大文字小文字を区別しない正規表現は 12 秒で、裏で全部の一致が揃う。
- テスト（`widgets/editor/editor_find_job_test.go`、race 検出器あり）: 4 MB を超える文書が裏で検索され、UI の goroutine の検索と同じ一致になる。読み込み中のファイルを正規表現で検索して、読み終わってから同じ一致になる。検索の goroutine を止めておいて、前、間、後ろの行を編集し、行を消してから進めると、編集後の文書を UI の goroutine で検索したのと同じ一致になる。新しい検索で古い検索が止まる。検索バーが「検索中…」を出し、Poster を通って件数を出す。
- 残り:
  - 大文字小文字を区別しない正規表現は、Go の `regexp` が先頭の文字列での絞り込みを使えず、全バイトを NFA で読むので遅い。区間を複数の goroutine に分ける、正規表現から必ず含まれる文字列を取り出して先に絞り込む、などで速くできる。
  - 4 MB を超える `SetText` の文書では、検索のたびに行のスライスを写す（500 万行で 80 MB）。
  - 検索を始めた後の編集が多いと、届いた結果を直す手間が編集の数に比例して増える。
