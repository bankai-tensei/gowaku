# 0146: Tester の操作は届かないノードでテストを落とす、表とシートのクリップ

決定日: 2026-11-17

状態: 採用

## 背景

初めて使う人に `gowakutest` を試してもらったところ、次のことが見つかった。

1. **誤った警告：** 高さに収まらないほど行の多い `collection.Table` で、`Tester.Warnings` が必ず「a child of collection.renderTable runs N px past its bottom edge」を報告した。表は自分の箱で描画を切り取り、表示域の行だけを作っているが、その RenderObject が `core.Clipper`（ADR 0132）を実装していなかった。調べると、行と見出しの RenderObject も、横にスクロールした列のセルを自分の外に置いたまま `Clipper` を実装しておらず、列が表より広いと行ごとに右端のはみ出しが出ていた。また、文字だけを入れた横の `overlay.Sheet` で「a child of overlay.renderSheetSlot runs 16 px past its right edge」が出た。シートは、窓の端にある角を丸く見せないよう、角の半径（16 px）だけ窓の外へ出して置いている。これはわざとで、窓の端が切り取るので見えない。
2. **黙って外れる操作：** `Tap`、`DoubleTap`、`DropFiles`、`DropText` などラベルで指す操作は、ノードの真ん中を押すだけだった。ノードが窓の外にある、祖先のクリップで丸ごと隠れている、上に描かれた物に覆われている、のどれでも、押下は別の物か何も無い所に届き、テストはそのまま進んだ（ドロップは `DropNone` を返すだけ）。`Find` の godoc には「タップの前にスクロールして見えるようにする」とだけ書いてあり、忘れても何も教えてくれなかった。半分だけ見える行では、真ん中がクリップの外にあると、見えている部分があるのに外れた。

## 選択肢

### シートのはみ出し

- **A. 配置を変え、角を窓の内に収める。** 窓の端の角を丸めない形にするか、窓の端にある角だけ半径を 0 にする。見た目が変わり、影も端で途切れる。
- **B. `renderSheetSlot` が自分の箱（オーバーレイの領域、ふつうは窓）で子を切り取り、`core.Clipper` を実装する。** 見た目は変わらない。描画にクリップが 1 つ増えるだけで、`Overlay` を窓より小さな所に置いたときも、角と出入りの途中のシートがその領域の外に出ない。
- **C. `Clipper` だけを実装し、描画では切り取らない。** 窓の端に任せることになり、`ChildClip` が描画と食い違う。

### 届かないノードの扱い

- **A. ラベルで指す操作が、届く点を選び、無ければテストを落とす。** 意味ツリーのノードの矩形を、窓と、祖先の `Clipper` の切り取りと重ね、見えている部分の真ん中を押す。そこが他の物に覆われていれば（その点のヒットテストの最も深い物が、ノードの RenderObject の中にも祖先にも無ければ）、見えている部分の格子の点を順に試す。どれも覆われていれば、真ん中を覆う物の型と、その物が開いた意味ツリーのノードの名前を書いて落とす。
- **B. 外れたことを戻り値で返す。** すべての操作の形が変わり、戻り値を見ないテストは今までどおり黙って進む。パッケージの「できなければテストを落とす」流儀（ADR 0141）にも合わない。
- **C. 警告として `Warnings` に出す。** 操作の直後に見る人はいない。

位置で指す操作（`TapAt` など）は、テストが点を自分で決めているので、そこにある物に届けば良く、何も無くても良い（何も無い所を押して閉じるメニューなど）。窓の外の点だけは、どの物にも届かないので落とす。

## 決定

1. `collection` の `renderTable` は自分の箱を、`renderTableHeader` は自分の箱を、`renderTableRow` は見出しより下の自分の部分を、`renderTableCell` はウィジェットのセルのとき自分の箱を、`ChildClip` として返す。どれも、表の `Paint` が実際にその範囲で切り取って描いているものである。
2. シートは選択肢 B。`renderSheetSlot` は `Paint` で自分の箱に切り取り、`ChildClip` で同じ矩形を返す。
3. ほかの RenderObject を、描画でクリップを使うファイルから探した。子をクリップするのに `Clipper` が無かったのは上の 5 つだけだった（`RenderImage`、`RenderProgressBar`、`RenderEditable`、エディター、時計の文字盤、木の行の文字は子を持たないか、子ではなく自分の文字を切り取る）。`Hero` の飛行は ADR 0141 のとおり扱わない。
4. 届かないノードは選択肢 A。`Tap`、`SecondaryTap`、`MiddleTap`、`DoubleTap`、`Hover`、`Scroll`、`Drag`、`Press`、`DropFiles`、`DropText` が同じ規則に従う。失敗の文は、操作の名前、ノードのラベルと矩形、窓の大きさ、どちらの外か（「is below the bottom of the 300x200 window; scroll it into view」）、隠した `Clipper` の型とその見える範囲、または覆う物の型とその名前を書く。大きさの無いノードは、その位置が窓の中なら届くとする。クリップは `core.Transformer` の変形をたどる（ポインターも動かす変形）。描画だけを動かす `PaintTransformer` はポインターを動かさないのでたどらない。
5. 位置で指す操作（`TapAt`、`SecondaryTapAt`、`MiddleTapAt`、`DoubleTapAt`、`HoverAt`、`ScrollAt`、`DragAt` と `PressAt` の始点、`DropFilesAt`、`DropTextAt`）は、点が窓の外のときだけ落とす。`MoveTo` は押したまま窓の外へ出られるので調べない。
6. ノードの持ち主の RenderObject を知るため、`target` は `Semantics` ではなく `SemanticsTree` で木を作る（`SemanticsOwner` は後者でしか埋まらない）。選び方は `Find` と同じ。
7. `Tap` の godoc に規則を書き、ほかのラベルの操作から参照し、パッケージの説明と `Find` の godoc にも 1 文ずつ足した。テストのガイド（en、ja）に 1 文足した。

## 結果

- 行の多い表、列が表より広い表、文字だけのシート（右、左、下）で、`Warnings` は何も報告しない。テストは、修正を外すと表で行ごとに右端と、表の下端のはみ出しが、シートで 16 px のはみ出しが出ることを確かめた上で、修正後に 0 件であることを確かめる。
- 窓の外のノード、`Scroll` の表示域の外のノード、全面を覆う押せる物の下のボタン、窓の外の点への `TapAt`、窓の外のノードへの `DropText` で、テストが理由つきで落ちる。表示域の下端にまたがる行は、真ん中が表示域の外でも、見えている部分が押される。
- リポジトリの既存のテスト（`gowakutest`、`widgets` の各パッケージ、根のパッケージ、`examples`、`gowakupreview`、`markdown`）は、黙って外れる操作に頼っておらず、直す所は無かった。
- 覆いの判定はヒットテストによる。ポインターを受けない飾り（`SelfHitTester` で通す物）は覆いにならず、受ける物（スクリムやバッジなど）は覆いになる。実際のクリックと同じ判定である。何も無い所を押してメニューを閉じるテストは、`TapAt` を使う。
