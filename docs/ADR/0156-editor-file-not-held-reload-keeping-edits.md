# 0156: Windows ではファイルを開いたままにしない、表示中の行の中身の変化に気づく、編集を残して読み直す

決定日: 2026-11-18

状態: ADR 0157 で置き換え（ファイルの変化の扱いはアプリの側に移した）

## 背景

ADR 0155 の「残り」の 3 つを片付ける。

1. **Windows では、こちらが開いている間、ほかのプログラムがファイルを置き換えられない。** ほかのエディタの「一時ファイルに書いて差し替える」保存が `Access is denied` で失敗する。
2. **書き換えに気づいても、読み直すと編集が消える（`Reload`）。**
3. **大きさも更新時刻も変えずに中身だけを変える書き換えには気づかない。**

## 選択肢

### 1. Windows での開き方

- **A. `FILE_SHARE_DELETE` を付けて開く。** 試したところ、削除はできるようになったが、**名前を変えて上から置く操作（`MoveFileEx` の上書き）は、共有を付けても開いている間は失敗した。** 置き換えの対象が開かれていると、Windows は POSIX の意味での置き換えをしない。しかも `syscall` は `platform` と `gpu` の外では使わない決まり（CODING_STYLE §8）があり、`widgets` からは使えない。
- **B. Windows ではファイルを開いたままにしない。** 行を読むときだけ開いて閉じる（読むのは行の塊のキャッシュに無いときだけ）。索引、検索、保存の goroutine は、走っている間だけ自分で開く。開くたびに `os.SameFile` で同じファイルかを確かめ、置き換えられたファイルを古いファイルとして読み違えないようにする。
- **C. ファイルを丸ごと写してから開く。** 数 GB を写すことになり、すぐ開くという目的に反する。

### 2. 編集を残して読み直す

- **A. 読み直すときに、古いファイルから「編集が置き換えた行」と前後の行を読み、新しいファイルの中で探して編集を当てる（patch と同じ）。** ただし、その場での書き換えや Windows での置き換えでは、古いファイルがもう読めない。
- **B. 編集するときに、編集が置き換えるファイルの行と前後 2 行を覚えておき、読み直すときはそれを使って探す。** 古いファイルが読めなくても編集を当てられる。
- **C. 3 方向のマージ（diff）。** 数 GB の 2 つのファイルの差分を取ることになる。

### 3. 中身だけの変化

- **A. 全体のハッシュを取る。** 全体を読むことになる。
- **B. 最後に読んだ行の塊（ほぼ画面に出ている行）と末尾 4 KB の FNV-1a のハッシュを持ち、確かめるときに読み直して比べる。** 利用者が見ている所の変化には必ず気づき、読む量は数 KB で済む。

## 決定

1 は B、2 は B（古いファイルが読めれば A も使う）、3 は B。

### ファイルを開いたままにしない（Windows）

- `holdOpen` はビルドタグで決まる定数で、Windows は偽、ほかは真。偽のときは `fileSource.handle()` が呼ばれるたびに開き、`os.SameFile` で確かめ、終わったら閉じる。真のときは開いたままのファイルを返す。開いたままのファイルは `atomic.Pointer` に持ち、goroutine からも安全に読める。
- 置き換えられた後、Windows では古い中身がもう読めない。そのため、別のパスへの `SaveAs` で古い中身を写せるのは、開いたままにする OS だけになる。
- 試しに、443 MB のファイルの読んだことのない場所へ 200 回飛んだところ、1 フレームの平均は 1.8 ms、最長 7.4 ms（新しい行のレイアウトを含む）で、開き直しの費用は目立たなかった。

### 表示中の行の中身の変化

- 行の塊を読むときに、読んだバイトの範囲と FNV-1a の合計（`span`）を持つ。最後に読んだ 4 つの塊を `recent` に覚え、その範囲を `atomic.Pointer` で見張りの goroutine に渡す。
- `CheckFile`（`probe`）は、大きさと時刻が同じでも、その範囲と末尾 4 KB を読み直して比べ、違えば `FileRewritten` を返す。見張りの goroutine も、毎回の `os.Stat` に加えて同じ範囲を読み直す（1 回に数 KB）。中身の変化は、次に大きさか時刻が変わるまで 1 度だけ知らせる。
- 画面に出ていない場所の、大きさも時刻も変えない書き換えには、今も気づかない。

### 編集を残して読み直す

- `lineBuffer.keep` は、編集がファイルの行を切るときに、置き換えるファイルの行（4,096 行まで）と前後 2 行を、ファイルの行番号ごとに `saved` に覚える。
- `Controller.ReloadKeepingEdits()` は、新しいファイルを開いて全部の行を索引してから、ピースの並びから編集の塊（ファイルの何行目から何行目が、どの行に置き換わったか）を作る。塊の両端の、変わっていない行（行を打って改行したときに置き換わったことになる元の行など）は削って小さくする。各塊について、置き換えた行と前後 2 行が並んでいる場所を、新しいファイルの中で、元の位置（それまでの塊のずれを足したもの）から外側へ探す（最大 13 万行）。見つかれば当て、見つからなければ `EditConflict{Line, Removed, Inserted}` として返す。文書は、新しいファイルに、当てられた編集だけを載せたものになる。
- 元に戻す履歴は消え、キャレットは先頭に行く。新しいファイルを索引し終わるまで返らない。

## 結果

- テスト: 置き換え（名前を変えて上に置く）と削除が、Windows でもこちらが開いている間にでき、`FileReplaced` として気づく。表示中の行を、大きさと時刻を戻して書き換えると、`CheckFile` も見張りも気づく。上に 3 行足されて離れた行も変わったファイルに、3 つの編集（変更、挿入、削除）がずれて正しく当たり、保存できる。編集した行をほかのプログラムも変えていれば `EditConflict` になり、ほかの編集は当たる。名前を変えて置き換えられ、Windows では古いファイルが読めなくなっていても、覚えておいた行で編集が当たる。編集が無ければ、ただの読み直しと同じ。race 検出器あり。
- 残り:
  - 索引、検索、保存の goroutine が走っている間（大きなファイルや遅い正規表現では秒から十数秒）は、Windows ではほかのプログラムがファイルを置き換えられない。
  - 4,096 行を超える範囲を置き換えた編集は、古いファイルが読めるときだけ当てられる。
  - `ReloadKeepingEdits` は新しいファイルを全部索引するまで UI を止める。
