# 0018: 起動時にフォントを並行して読む

決定日: 2026-11-07

状態: 採用

## 背景

ADR 0015 で、起動が Gio より 31ms 遅かった。段階ごとの計時は次のとおり。

| 段階 | 時間 |
|---|---:|
| Win32 の初期化 | 約 5ms |
| D3D11 デバイス | 約 45ms |
| フォント索引の読み込み | 約 40ms |
| 最初の日本語シェイピング | 約 45ms |

後ろの 2 つは GPU と無関係なのに直列に並んでいた。最初のシェイピングが重いのは、go-text が日本語フォントの `glyf` 表を全部解析するから。

## 決定

`Run` の最初に `loadShaper` でゴルーチンを起こし、ウィンドウとデバイスの作成と並行してフォントを読む。`aあ亜` を 1 度シェイピングして、日本語フォントまで読み終えておく。`run` に入る前に受け取るので、Shaper に触るのは常に 1 つのゴルーチンだけ。規約 §9 の「UI はメインゴルーチン専用」は保たれる。

英語だけのアプリも日本語フォントを読むことになる。別のコアで動くので起動は遅れず、ヒープが約 40MB 増える。gowaku の中心は日本語なので受け入れる。

## 結果

起動中に GC が別のゴルーチンの割り当てで走るようになり、Vulkan の隠れたバグが表に出た。`ptr` で `uintptr` にした構造体が C の呼び出し中に回収され、`vkCreateInstance` の失敗と SIGSEGV が 12 回に 2 回起きた。`kept` のリングで直した（ADR 0013）。修正後は 150 回連続で成功し、`GOGC=1` でも Vulkan のテストが通る。

このバグ自体は前からあった。並行読み込みのせいではなく、GC の時機が変わって見えるようになっただけ。
