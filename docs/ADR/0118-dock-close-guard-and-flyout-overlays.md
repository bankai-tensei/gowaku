# 0118: ドックのパネルを閉じる前に聞く、フライアウトから開いたオーバーレイ

決定日: 2026-11-14

状態: 採用

## 背景

gowaku で作るコードと Markdown の閲覧アプリから二つの要望が来た。

- **#19 閉じる前に止めたい。** タブの × や Ctrl+W は、DockLayout がパネルを閉じてから `OnClose` で知らせる。未保存のタブで「保存しますか」を聞けず、取り消しもできない。
- **#21 フライアウトから開いたメニューやダイアログでフライアウトが隠れる。** 自動で隠れる帯のパネル（ADR 0102）をフライアウトに出し、中で右クリックしてコンテキストメニューを開くと、フォーカスがメニューへ移った時点でフライアウトが隠れる。アプリは覚えておいて出し直しているが、一度畳まれてまた出るのが見える。

## 選択肢

### #19 の形

1. `CanClose func(id string) bool`。同期の問い合わせ。
2. `OnCloseRequest func(id string)` を通知だけにして、閉じるのはいつもアプリが `DockController.Close` を呼ぶ。
3. `OnCloseRequest func(id string) bool`。false なら閉じずに残し、アプリは答えが出たら `DockController.Close` を呼ぶ。ウィンドウの `OnCloseRequest`（ADR 0076）と同じ形。

### #21 の「内側」をどう知るか

1. ドックがメニューやダイアログの種類を知って、それぞれを特別に扱う。
2. オーバーレイのエントリーが、開いた場所（`InsertFrom` の `ctx`）を持っていることを使う。「内側か」を確かめるとき、エントリーの一番上まで来たら、親ではなく開いた場所の render object へ移って上り続ける。
3. core に「フォーカスの持ち主」の木を足す。

## 決定

#19 は 3、#21 は 2。core には手を入れていない。

### 1. 閉じる前に聞く（#19）

- **API。** `DockLayout.OnCloseRequest func(id string) bool`。
  - ユーザーが閉じる操作をしたとき、閉じる前に呼ぶ。false ならパネルは残る。nil なら閉じられるパネルはすぐ閉じる（今まで通り）。
  - 同期の bool にした理由は ADR 0076 と同じ。閉じ方が 1 つで済み、新しい型が要らない。gowaku のダイアログ（`overlay.ShowDialog`）は非同期なので、ダイアログを開いて false を返し、答えが出たら `DockController.Close(id)` を呼ぶ。
  - 2 の「いつも通知だけ」は、確かめることの無いアプリにも `Close` を書かせることになるので採らなかった。
- **聞く道。** すべて 1 箇所（`dockState.mayClose`）を通る。
  - タブの ×、タブの上の中ボタン、Ctrl+W / Ctrl+F4（群の帯とフライアウトの中の両方）、フライアウトの見出しの ×。
  - 閉じられない（`Closable` が偽の）パネルには聞かない。
- **聞かない道。** `DockController.Close` はコードからの閉じ方で、聞かない。保留した閉じ方を、確かめた後に進めるのがこれ。
  - `Close` は今まで通り `OnClose` も `OnChange` も呼ばない。呼んだアプリは、`OnClose` でしていた後始末と配置の保存を自分でする。doc コメントに書いた。
  - パネルの一覧（`Panels`）から外したパネルも、聞かずに消える（アプリ自身がしたことなので）。
- **「他を閉じる」「すべて閉じる」。** DockLayout にも TabBar にも、そういうメニューは無い。アプリが作るなら、アプリが自分で確かめて `Close` を呼ぶ。
- **TabBar。** 新しい API は足さない。
  - TabBar の `OnClose` は、もともと「閉じてほしい」という頼みで、タブを消すのはアプリが `Tabs` から外したとき。`OnClose` の中で聞いて、後で外す（または外さない）ことが今でもできる。
  - 同じことに口を二つ作ると、どちらを使うかで迷う。doc コメントに、自分では何も外さないことと、後で外してよいことを書き足した。
  - `TabItem` / `TabGroup` には手を入れていない。
- **ギャラリー。** ドックの頁で、文字を書き換えたエディタを閉じると「変更を破棄しますか」を聞くようにした。

### 2. オーバーレイの持ち主（#21）

- **何が起きていたか。**
  - オーバーレイは窓の一番上の `Overlay` の Stack にあり、ヒットテストでドックより先に当たる。そのため、メニューを押してもドックの「外を押した」には届かない。押下は原因ではなかった。
  - 原因はフォーカス。メニューやダイアログはフォーカスを取る。フライアウトのスロットの `FocusWithinChanged(false)` が来ると、ドックは移った先が自分のフライアウトか帯かを確かめ、違うので隠していた。
- **`overlay.Contains(region, ro core.RenderObject) bool`。**
  - ro が region か、その下か、region の中から `Host.InsertFrom` で開いたエントリー（メニュー、ポップアップ、ダイアログ、ツールチップ）の中か、を返す。エントリーが開いたエントリーも、たどって数える。
  - 仕組み: 各エントリーの一番上の render object（今までもあった `renderEntryHits`）にエントリーを持たせた。親をたどって、ここに来たら、開いた場所（`from.RenderObject()`）へ移る。
  - 場所の無いエントリー（`Insert`、トースト）は、`Overlay` を持つものの中にだけある。
  - 循環は起きない。エントリーを開く場所は、そのエントリーより先にある。
- **`overlay.EntryFocusListener`（`EntryFocusLeft()`）。**
  - フライアウトからメニューへ移るときは、フライアウトの `FocusWithinChanged(false)` が来る。しかし、その後でメニューからよそへ移るときは、フライアウトには何も来ない（もう中に無いので）。これだけだと、メニューの項目がフォーカスを別のパネルへ移したときに、フライアウトが出たまま残る。
  - そこで、`renderEntryHits` が `core.FocusWithinListener` になり、フォーカスがエントリーから出たら、開いた場所から上（`Contains` と同じたどり方）の `EntryFocusListener` に知らせる。知らせるのはフォーカスが移った後なので、`Focused()` は新しい先を返す。
  - 既存の `FocusWithinChanged` を二度呼ぶ案は採らなかった。core の「true と false が対になる」約束（ツールチップなどが頼っている）を崩す。
- **ドック。**
  - `focusStaysNear` は、フライアウト、その見出しと取っ手、帯のスロットのどれかが、`overlay.Contains` で今のフォーカスを含むかを見る。
  - `renderDock` が `EntryFocusListener` になり、知らされたら同じ確認をして、近くに無ければ隠す（`keepFlyoutNear`）。入れ子のドックでは、外側のドックにも届く。
  - 押下の判定は変えていない。オーバーレイを押しても、ドックには届かないため。
  - メニューやダイアログは閉じるとき、開く前のフォーカス（フライアウトの中）に戻す（ADR 0046）。そのため、閉じた後もフライアウトは出たままで、キーボードも中にある。
- **`DockPanel.Build` の ctx。**
  - 今までは、ドック自身の Build の ctx をそのまま渡していた。その ctx でダイアログを開くと、開いた場所はドックの外側の render object になり、フライアウトの内側に数えられない。
  - パネルの中身を `basic.Builder` で包み、Build にはパネルの場所の ctx を渡すようにした。アプリが一番手近な ctx で `ShowDialog` を呼べば、そのパネルのものになる。
  - 見つかる Theme や Localizations は同じ（ドックとパネルの間に何も足していない）。中身の State も、初めから同じ形の木なので保たれる。
- **他の自動で閉じる面。** ポップオーバー、コンボボックス、日付の選択など、外を押すかフォーカスが出たら閉じるものも、`Contains` と `EntryFocusListener` で同じことができる。今回は `widgets/nav` と `widgets/overlay` の外には手を入れていない。
- **ギャラリー。** アウトライン（右の帯のフライアウト）にコンテキストメニューを付けた。項目の一つはダイアログを開く。

## 結果

- 追加だけ。`OnCloseRequest` が nil なら、閉じ方の動きは今まで通り。
- テスト（GPU 無し）。
  - `TestDockLayout_CloseRequest`: ×、中ボタン、Ctrl+W、Ctrl+F4、フライアウトの Ctrl+W と × で、聞いて残すこと、許せば閉じて知らせること、閉じられないパネルには聞かないこと、`Close` は聞かず知らせないこと、State が残ること。
  - `TestTabBar_OnCloseMayHoldTheTab`: `OnClose` が外さなければタブは残る。
  - `TestDockLayout_OverlaysFromAFlyoutKeepItOut`（gowakutest）: フライアウトで右クリック → メニュー → 項目を選ぶ → 出たままで、キーボードも中。Escape でメニューだけ閉じる。メニューからダイアログ → 閉じる → 出たまま。メニューの横を押すとメニューだけ閉じる。本当に外を押すと隠れる。フォーカスがメニューから別のパネルへ、または無しへ移ると隠れる。
  - `TestContains_FollowsEntriesToTheirPlaces`: 入れ子のエントリー、場所の無いエントリー、よその場所のエントリー、nil、`EntryFocusLeft` が届く範囲。
- 残り:
  - `Overlay` をフライアウトの中に自前で置いたとき、そのエントリーがフライアウトの外にはみ出した部分を押すと「外」になる。窓の `Overlay` を使う普通の場合には起きない。
  - フォーカスを持たずに開くオーバーレイ（ツールチップ）は、もともとフライアウトを隠さない。
  - 実機での確認（閲覧アプリの画面、スクリーンリーダー）はしていない。
