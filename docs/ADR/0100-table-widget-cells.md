# 0100: Table のセルにウィジェットを置く（CellWidget）

決定日: 2026-11-13

状態: 採用

## 背景

当初の計画の `Sparkline` は「Table のセルに入る折れ線と棒」として作った（ADR 0095）。ところが `collection.Table` のセルは表が自分で描く 5 種類（ADR 0071）だけで、ウィジェットを置く道が無かった。ADR 0095 では gallery の表を `Row` と `Divider` で組み、「Sparkline を本物のセルに入れるには Table に手が入る」と残していた。

ADR 0071 は「セルごとに利用者のウィジェットを置く」（選択肢 1）を、スクロールのたびに見えている行を Build し直すことになるとして見送り、「要望が来たら、見えている行だけを Build する別の道として考える」と書いた。今回がその要望にあたる。

制約:

- 表は 100 万行を 0 allocs/op でスクロールする。文字や数のセルの道は変えない。
- `collection`（段 6）は `control`（段 3）を import してよいが、表が Sparkline を知ることはしない。ウィジェットは利用者が渡す。
- 当初の計画の互換方針のとおり追加だけにする。既存の公開 API、振る舞い、golden は変えない。

## 選択肢

1. **セルに一般のウィジェットを置く。** `Widget func(T) core.Widget` を列に持たせ、見えている行のセルにだけ部分木を作る。ウィジェットは自分でレイアウトし、描き、ポインタとキーボードを受け、Semantics を出す。
2. **「描くだけ」のセルのフック。** `Paint func(T, *paint.Canvas, geom.Rect)` のように、表の描画の中で利用者に描かせる。ウィジェットの木を作らないので速い。
3. Sparkline を表の 6 つ目の種類（`CellSparkline`）として表の中で描く。

## 決定

1 にした。

- 2 では `control.Sparkline` をそのまま入れられない。Sparkline の描画オブジェクトは公開しておらず、描くための関数を `control` に足すか、利用者が同じ絵を描き直すことになる。描くだけなので Semantics（Sparkline の画像のノード）も、ボタンのような操作も入らない。
- 3 は表が Sparkline に依る。種類を足すたびに表を直すことになり、ADR 0081 の層の考え（表は部品を受け取る側）にも合わない。
- 1 の重さは、Build を「行が入れ替わった行のオブジェクトだけ」に絞れば抑えられる。下の 3 で、スクロールの 1 段で行が入れ替わらないフレームは 0 allocs、利用者がウィジェットを作り置けば行が入れ替わるフレームも表の側は 0 allocs にした。

### 1. API

足したのは `CellKind` の定数 1 つと `TableColumn` のフィールド 1 つ。ほかの種類と同じく「種類を選び、行ごとのデータを関数で読む」形にした。

```go
collection.TableColumn[Station]{
	Title: "24 時間の気温", Width: 168, Kind: collection.CellWidget,
	Text:   func(s Station) string { return s.TrendText },   // 読み上げ、絞り込み、コピーの文字
	Widget: func(s Station) core.Widget { return s.TrendCell }, // 作り置いた control.Sparkline
}
```

- `CellWidget`: `Widget` が返すウィジェットを見せる。`Text` は見せない。
- `Widget func(row T) core.Widget`: nil、または nil を返すとセルは空。
- `Kind` が `CellWidget` でなければ `Widget` は読まない（`Value` を `CellText` の列が読まないのと同じ）。

### 2. 置き方

- セルの中は、列の幅から左右の余白（`tablePadding`、12）を、行の高さから上下 4 を引いた広さを上限にした緩い制約。ウィジェットは自分の大きさを選ぶ。高さ 32 の行で、高さ 24 の小さいボタン（`ButtonSmall`）がそのまま入り、高さを指定しない Sparkline は 24 いっぱいに描く。
- 位置はセルの始め、`Trailing` なら終わり。高さは真ん中。
- 描くのは表。ほかのセルと同じく行の順に描き、セルの矩形で切る。固定列の下に潜る列は、今までどおり固定列の右で切られる。選択とホバーの地はウィジェットの下に描く。

### 3. 行の使い回しと Build

表の行のオブジェクトは、見えるだけの数（`poolSize`）を作り、行 i をオブジェクト i mod 数 に割り当てる（ADR 0058）。割り当てはレイアウトで決まり、スクロールでは何も Build しない。

ウィジェットのセルは、行のオブジェクトの中に「ホスト」（StatefulWidget）を置き、その State が「このオブジェクトが今見せる行」のウィジェットを Build する。

- スクロールが動くたび（`ScrollState.OnMove`、レイアウトの前）に、各ホストに「自分のオブジェクトが見せる行」を計算させ、作った行と違うホストだけ `SetState` する。同じフレームのうちに Build され、レイアウトの割り当てと揃う。行が変わらないフレームは、ホストの数だけ整数を比べるだけ。
- 行を見せていないオブジェクト（見える行が数より 1 つ少ないとき、毎回 1 つ出る）は、前のウィジェットを隠したまま持つ。空のウィジェットに替えると、次に行を見せるときに部分木を作り直すことになり、1 行進むごとにアロケーションが出た。
- 行の数や表の大きさが変わってオフセットが詰められた場合は、レイアウトの最後にも見直す。行の数が減ったときは Build の中でオフセットの上限を先に詰め、最初のフレームから正しい行を作る。
- 作った行と見せる行が違うウィジェット（ホストが Build を待つ 1 フレーム）は、描かず、当てず、Semantics にも出さない。違う行のウィジェットが一瞬でも見えることは無い。
- `renderTable.ChildAt` は、ウィジェットのセルがある表では行のオブジェクトを行の順に返す。Tab が上の行から順にウィジェットを訪ねるため。ウィジェットの無い表の順番は変えない。

アロケーション:

- 文字・数・ほかの種類だけの表は今までと同じ道を通る（ホストは作られず、上の見直しはホストが無ければ何もしない）。`TestDataTable_ScrollingAMillionRowsDoesNotAllocate` と `TestDataTable_ScrollingCellKindsDoesNotAllocate` はそのまま通る。
- Sparkline の列: 行が入れ替わらないスクロールの 1 段は 0 allocs（`TestDataTable_ScrollingWidgetCellsDoesNotAllocate`）。行が入れ替わるフレームでは、入ってきた行の Sparkline が Build し直し、その中で描画用のウィジェットを `core.Widget` に入れるのでアロケーションが出る。これは Sparkline の Build の性質で、表の側ではない。
- Build しない RenderWidget を作り置いた列では、行が入れ替わるフレームも 0 allocs（同じテスト）。表の仕組みそのものは行の入れ替えで何も確保しない。
- 利用者の関数がウィジェットを毎回作ると、値を `core.Widget` に入れるので、入ってきたセルごとに確保が出る。doc コメントで、`Text` と同じく作り置くよう勧めた。

### 4. ポインタと選択

- 当たり判定はウィジェットを表より先に置く。押下を受け取ったウィジェット（ボタン）がそれを取り、表は選択も起動もしない。受け取らないウィジェット（Sparkline）の上の押下は表に届き、今までどおり選択し、ダブルクリックで `OnActivate` を呼ぶ。チェックの列（ADR 0071）の「箱を押すと選択は変えない」と同じ考え。
- ホバー（行の地）は今までどおり。

### 5. キーボードと焦点

表は Tab の 1 つの止まりで、中は矢印でセルを動く（ADR 0058）。ウィジェットのセルでは ARIA の grid の「セルの中のウィジェット」の形にした。

- キーボードを受けるウィジェット（ボタン）は、その行が見えている間、Tab の止まりになる。表の外から子孫を Tab から外す方法は core に無く（`Hider` は当たり判定と Semantics も隠す）、core には手を入れない。順番は焦点のセルの後、上の行から。
- ウィジェットがキーボードを持つと（押下でも Tab でも）、そのセルが焦点のセルになる（`FocusWithinChanged`）。選択は変えない。
- ウィジェットが使わなかったキーは表に上がる。矢印は隣のセルへ動き、キーボードもセルへ移る。Escape はセルに戻す。
- 焦点がセルにあるとき、Enter と F2 はセルの中で最初にキーボードを受けるものへ移す。受けるものが無ければ、Enter は今までどおり `OnActivate`。
- ウィジェットを持つ行がスクロールで外に出て、行のオブジェクトが別の行を見せると、キーボードは表に移る（見えていないセルの焦点と同じ扱い）。別の行のボタンに焦点が残ることは無い。

### 6. 編集、ソート、絞り込み、コピー

- **編集しない。** `Editable` でも編集の対象にしない（チェックの列と同じ）。Tab の編集送りも飛ばす。文字を打っても編集は始まらない。隣のセルの編集はそのまま動き、編集中にウィジェット（別の行のボタン）を押すと、エディタからキーボードが離れるので確定する。
- **ソートと絞り込みは利用者の仕事**（ADR 0058）。表はウィジェットを読めないが、もともと値で並べていないので、列に別の鍵を持たせる必要は無い。`Sortable` は見出しを押すと `OnSort` を呼ぶだけで、利用者は行の鍵（Sparkline なら最新の値など）で並べ替える。`Filterable` も同じで、絞り込みの文字は `Text` に照らすのが自然。doc コメントに「ウィジェットではなく行の鍵で並べる」と書いた。
- **コピー:** 表にコピーの機能は無い。利用者がコピーを作るときのセルの文字は `Text` とした（読み上げと同じ文字）。

### 7. 列の操作

- 幅を変えると、セルの制約が変わってウィジェットが組み直される（Sparkline は大きさが変われば線を作り直す）。
- 並べ替えでは、列の位置ごとにホストが更新され、新しい列のウィジェットを Build する。種類の違う列と入れ替わったセルは子が替わる。
- 固定列は今までどおり。

### 8. Semantics

- セルは grid cell のまま、名前は `Text`。その子に、ウィジェットのノード（Sparkline の画像、ボタン）を置く。チェックの列が grid cell の子にチェックボックスを置いた（ADR 0071）のと同じ形。
- 行の名前（見えている順のセルの文字をつないだもの）にも `Text` が入る。
- `Text` が無いセルは名前が空で、ウィジェットのノードだけが読まれる。Sparkline には `Label` を渡すことを勧める（ADR 0095）。

## 結果

- `control.Sparkline` が本物の `Table` のセルに入る。gallery の `pages_visual.go` の「表のスパークライン」を `collection.Table` に置き換えた。地点と現在の列で並べ替えられ、スパークラインは行と一緒に動く。カタログの Sparkline の絵は表を使っていないので変えていない。
- 既存の golden は変わらない（文字だけの表の道は同じ）。
- テスト（GPU 無し）: スクロール（端数、1 行、1 ページ、遠くへの飛び、ホイールの慣性）で各行のオブジェクトが自分の行のウィジェットだけを描くこと、置き方（幅、Trailing、行の高さ）、ソートと絞り込みの後、行が減ったときの最初のフレーム、列の幅と並べ替え、固定列、選択とダブルクリック、ボタンの押下と Space・Escape・Enter・F2・矢印、行が外に出たときの焦点、Tab の順番、隣のセルの編集、Semantics とスクリーンリーダーのタップ、ゼロ値、スクロールのアロケーション。
- ベンチ: `BenchmarkDataTable_ScrollStep_Sparklines`（2 万行、線と棒の列、1/3 行ずつ）と `BenchmarkDataTable_ScrollStep_SparklinesInRow`（行の中だけで動く）を足した。数字はまだ取っていない。

## 残したこと

- ウィジェットを Tab から外す手段（core の「Tab に入れない」印、または `Button` の `SkipTab`）。今は見えている行のボタンがそれぞれ Tab の止まりになる。
- ウィジェットの高さで行の高さを変えること。行はすべて同じ高さのまま（100 万行で見えている行を求めるための前提）。
- 見出しにウィジェットを置くこと。
- 表のコピー機能。

## 追記（2026-11-13）

- 行の数が減って何も表示していない行オブジェクト（`renderTableRow` の行番号が負）は `core.Hider` で隠れる。前の行のウィジェットを持ったままでも Tab がそのボタンに止まらない。描画・ヒットテスト・読み上げからは以前から外れていた。
