# 0007: テキストの構成と当初の計画からの変更点

決定日: 2026-11-07

状態: 採用

## 背景

Phase 3 で当初の計画のテキストの部分を実装すると、依存表と噛み合わない箇所と、実物のフォントで前提が崩れる箇所があった。

## 決定

### 既定フォントは Yu Gothic UI ではなく Yu Gothic

当初の計画は Windows の既定を Yu Gothic UI としていた。実測すると Yu Gothic UI はかなと約物がプロポーショナルで（「で「」の 2 文字が 16px で 20.8px）、始め括弧に詰めるべき半角の空きが無い。JLReq の規則は全角の字面を前提にしているので、全角の `Yu Gothic` を既定にする。

約物の詰めを適用するかは `Unit.FullWidth`（advance が em の ±2% か）で字形ごとに判定する。プロポーショナルなフォントを指定しても、空きの無い字形から半角を引くことはない。

### 和文の run ではカーニングを切る

Yu Gothic の GPOS は読点の前などを詰める（「する、」が 48px でなく 47.4px）。全角を前提とする組版と衝突するので、Han / Hiragana / Katakana の run では `kern` を切る。欧文の run は有効のまま。

### `Canvas.DrawText` はやめて `Canvas.DrawGlyphs`

当初の計画の `DrawText(layout *text.Layout, ...)` は `paint → text` の依存になり、規約 §3.1 の `text → paint` と循環する。paint には `GlyphRun`（`FaceID` と位置だけ）を置き、`text.Layout.Runs()` がそれを返す。paint はフォントを知らない。

### RenderParagraph は widgets に置く

規約 §3.1 で `layout` は `text` を import できない。表を変えず、`RenderParagraph` を `widgets/text.go` に置いた。

### Shaper は `core.Inherited` で配る

パッケージ変数は禁止なので、`app` が各ウィンドウのルートを `core.Inherited[*text.Shaper]` で包み、`Text.Build` が `DependOn` で取る。`core` は `text` を import せずに済んだ。Shaper が無い木で `Text` を使うと panic する。

### 行分割は Unit の列に対する純粋なアルゴリズム

`text/jlreq` は標準ライブラリだけに依存し、書記素クラスタを `Unit{Rune, Advance, Em, FullWidth, BreakAfter}` で受ける。規則のテストは合成メトリクスで書けるので、CI にフォントが無くても全規則が検証される。UAX #14 は欧文が関わる箇所だけに使い、和文どうしの境界は jlreq の規則で決める。

連数字（`１００`）の分離禁止を当初の計画の「数字と単位記号」の延長として足した。全角数字は UAX #14 では ID クラスで、どこでも切れてしまうため。

ゼロ値を既定にするため、`Punctuation` と `WesternSpacing` は否定形の bool ではなく列挙にした。

### アトラスは texel 等倍で、サンプラーを持たない

グリフは物理ピクセルにラスタライズし、Y は整数、X は 1/4 ピクセルに量子化するので、texel と画面のピクセルは 1 対 1 になる。シェーダーは `Load` で読み、サンプラーもパディングも要らない。`Instance.Radii` の先頭 2 要素に texel 座標を入れ、112 バイトのままにした。

Phase 6 のスケール遷移でグリフを拡大するときは、サンプラーとパディングが要る。（Phase 6 で見直した: ラスタサイズの量子化で足りたので作っていない。ADR 0010）

当初の計画の「16 枚までバインド」はやめて、DrawCall ごとに 1 枚にした。1 ページに 1 万字ほど載るので切り替えはまず起きず、シェーダーも単純になる。Phase 5 の画像で足りなくなったら見直す。

アトラスは 8 ページ（32MB）までで、超えたらそのフレームで使っていない最古のページを捨てる。

### 行送りは固定

`LineHeight`（既定 1.5）× `Size`。フォールバックが混ざっても行が揃い、Yu Gothic の大きな line gap にも左右されない。

## 含めなかったもの

- **両端揃え**: 当初の計画に無い。Word の既定は両端揃えで、Word と違う行分割になる。Word はそこで字間も圧縮するため、左揃えでしか比較できない。
- **RTL**: 段落は LTR 固定で、アラビア語などはクラスタの順に左から並ぶので正しく読めない。当初の計画も触れていない。v2 候補。
- **タブ**: 空白 1 個として扱う。TextField（Phase 4）で必要なら見直す。
- **合字の内側のキャレット**: 合字はクラスタ全体で 1 単位にしている。

## 結果

Word と同じ文章・同じ幅で行分割を突き合わせた。Word に組ませて行分割を書き出すスクリプトと、`examples/jptext` の `-lines` の出力を比べた。

- 約物の詰めを両方で切ると、7 条件 312 行のうち違いは 1 箇所。
- 詰めは gowaku の既定のままだと約物の密集した段落だけ分割が変わる。Word は左揃えでは約物を詰めないため。

性能（Iris Xe、150%、12,890 グリフ）:

| 計測 | 結果 |
|---|---|
| 1000 個のシェイピング + 行分割 | 11.5〜13.6ms |
| 上に加えて初回の全処理（ラスタライズ、テクスチャ作成、転送、描画） | 16.3〜18.7ms |
| 再描画の CPU 時間 | 1.7〜1.9ms |
| paint / Encode のアロケーション | 0 |

初回フレームは 16ms を少し超える。プロファイルでは大半が HarfBuzz とフォント解決で、自前の処理ではない。
