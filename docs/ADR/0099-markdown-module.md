# 0099: Markdown は別モジュールで、パーサは自前で持つ

決定日: 2026-11-13

状態: 一部を ADR 0107、ADR 0119 で置き換え

## 背景

当初の計画に `Markdown` があり、「パーサの依存が増える（当初の計画の『新しい依存は 3 つだけ』に触れる）。作るなら別モジュール」とだけ書いてあった。範囲の判断はこちらに任された。

要るのは次の 3 つ。

- 本体（`github.com/bankai-tensei/gowaku`）の依存を増やさない。`go build ./...` も `golangci-lint run` も今までどおり。
- README やヘルプ、チャットのログのような、アプリが普通に見せる Markdown がそのまま出る。日本語が正しく折り返す。
- どんな文字列を渡しても panic せず、止まらない。Markdown は外から来ることが多い。

## 決定

### 1. 入れ子のモジュール `markdown/`

リポジトリの中に `markdown/go.mod`（`module github.com/bankai-tensei/gowaku/markdown`）を置く。本体への参照は `examples/bench` と同じく `replace github.com/bankai-tensei/gowaku => ../` で、go.work は作らない。

- 本体の `go build ./...` / `go test ./...` / `golangci-lint run` は入れ子のモジュールを見ない（`./...` はモジュールの境で止まる）。本体の go.mod と go.sum は変えていない。
- 入れ子のモジュールは本体のウィジェット層（`widgets/basic`, `widgets/interact`）とその下の層だけを import する。本体からは import しない。カタログ（`examples/gallery`）に載せられないのはこのため。見本は `markdown/example` に置いた。
- 依存は本体と `golang.org/x/text`（全角かどうかの判定）だけ。どちらも本体がすでに持っているので、利用者の依存グラフに新しいものは増えない。
- 公開のときは、入れ子のモジュールに `markdown/v0.x.y` の形のタグを打つ。replace は公開したモジュールを使う側には効かないので、そのときは本体の版を require に書く。

ビルドとテストは `markdown/` で行う。

```
cd markdown
gofmt -s -l . && go vet ./... && golangci-lint run ./...   # lint はルートの .golangci.yml を使う
go test -race ./...
go test -run '^$' -fuzz FuzzParse -fuzztime 30s .
GOOS=linux CGO_ENABLED=0 go build ./...
go run ./example
```

### 2. パーサは自前で書く（goldmark に依らない）

選択肢は 2 つあった。

| | 自前（CommonMark の一部） | yuin/goldmark |
|---|---|---|
| 依存 | なし | 1 つ（純 Go、モジュールキャッシュにもあった） |
| 大きさ | コメント込みで約 2,300 行 + テスト | 大きい。拡張の仕組みごと入る |
| 日本語の改行 | 自分で決められる | 東アジアの改行の拡張はあるが、出力が HTML 前提の AST |
| 深さの制限・病的な入力 | 自分で入れる | 中に手を入れられない |
| 仕様への忠実さ | 範囲内は CommonMark の手順どおり | ほぼ完全 |

自前にした。理由:

- 欲しい範囲（下の表）は、CommonMark 仕様の付録にある 2 段の手順（ブロックを行ごとに開閉し、インラインは区切り文字のスタックで強調とリンクを決める）をそのまま書けば、コメント込みで 2,300 行ほどで収まる。commonmark.js と同じ形なので、読む人が仕様と突き合わせられる。
- 依存ゼロなら、このモジュールを使う人も「本体 + x/text」だけを監査すればよい。
- 日本語の扱い（後述の改行と強調）と、入れ子の深さの制限を、パーサの中で素直に決められる。
- AST をウィジェットに変えるところは、どちらを選んでも自分で書く。goldmark を入れても減るのはパーサだけ。

AST は公開しない。公開 API はウィジェットだけにして、パーサの作りを後で変えられるようにした。

### 3. 対応する書き方

| 書き方 | 対応 | 備考 |
|---|---|---|
| ATX 見出し `#`〜`######` | ○ | 閉じの `#` も |
| setext 見出し（`===` / `---` の下線） | ○ | 安く書けたので入れた |
| 段落、ソフト改行、ハード改行（行末の空白 2 つ / `\`） | ○ | |
| `*強調*` `**強い強調**` `~~取り消し~~`（`~` 1 つも） | ○ | 3 の規則も仕様どおり |
| コードスパン | ○ | |
| フェンス（```` ``` ```` / `~~~`）、字下げのコードブロック | ○ | 等幅、横スクロール、言語名を表示。色付けはしない（`Highlight` の口だけ） |
| 引用（入れ子、遅延継続行） | ○ | |
| 番号・箇条書きのリスト、入れ子、緩い / 詰めたリスト | ○ | |
| タスクリスト `- [ ]` / `- [x]` | ○ | 読み取り専用のチェックボックス |
| リンク（インライン、参照、`<自動リンク>`、裸の `www.` / `http(s)://`） | ○ | |
| 画像 | ○ | 相対パスの画像は `Images`（`fs.FS`）から PNG / JPEG / WebP を読んで出す。`ImageProvider` が先。ネットワークからは取得しない |
| 区切り線 | ○ | |
| GFM の表（揃え、欠けたセル、`\|`） | ○ | |
| 文字参照 `&amp;` `&#12354;` | 一部 | 数値参照は全部。名前付きは文章でよく使う約 40 個だけ（HTML の 2,000 余りは持たない）。知らない名前はそのまま出す |
| 生の HTML（ブロック・インライン） | 一部 | （ADR 0119 で置き換え）README で使う安全な部分集合（`p` / `div` / `h1`〜`h6` の `align`、`details`、`img`、`picture`、`a`、`b` など）を解釈し、ほかのタグは書いたままの文字として出す。HTML ブロックは CommonMark の規則で見つける |
| 脚注、定義リスト、数式、絵文字の `:name:` | × | GFM でも拡張。要望が出てから |
| 裸のメールアドレスの自動リンク | × | `<a@b.c>` の形だけ |

### 4. 日本語

- **ソフト改行**: 改行の前後がどちらも全角（East Asian Wide / Fullwidth）なら何も入れず、それ以外は空白 1 つにする。「日本語の\n文章」は「日本語の文章」になる。改行位置はライブラリの行分割（JLReq）が決めるので、Markdown 側では折り返しに手を出さない。
- **強調の区切り**: CommonMark の左右の flanking の判定で、区切りの隣の全角文字を約物として扱う。そのままの仕様だと `これは**「重要」**です` が強調にならない（閉じの `**` の前が約物で後ろが文字のため）。全角を約物とみなすと、単語の間に空白を入れない日本語で `**` / `_` が素直に効く。英語の判定は変わらない。
- **裸の URL**: GFM は空白まで URL に含めるので `https://example.com/aを参照` の「を参照」まで URL になる。ASCII 以外の文字で URL を終える。

### 5. ウィジェット

```go
type Markdown struct {
	core.StatefulBase
	Source        string
	OnLinkTap     func(url string)
	Images        fs.FS
	ImageProvider func(src, alt string) core.Widget
	Highlight     func(lang, code string) []text.Span
	Styles        Styles
}
```

- ゼロ値で使える（何も出さない）。見た目はテーマから決め、`Styles` の非ゼロのフィールドで上書きする。本文の既定は `Text.Reading`。
- 解析は `Source` が変わったときだけ。State に解析済みの木を持ち、同じ文字列で作り直しても解析しない。`OnLinkTap` は State の 1 つの関数を通して呼ぶので、親が毎回新しいクロージャを渡しても子のウィジェットは変わらない。
- 段落は `RichText` と同じく `text.Shaper.ShapeSpans` で組む。ただし `RichText` にはリンクを押す口、コードの地、取り消し線が無いので、モジュールの中に `richText`（RenderObject）を持った。リンクは段落の子の RenderObject で、リンクが掛かる各行の矩形だけでポインタを受ける。行をまたぐリンクでも、どの行を押しても同じ宛先になり、ホバーで全部の行に下線が出る。Tab でフォーカスを受け、Enter で開き（ブラウザと同じく Space は使わない）、キーボードで来たときはフォーカスリングを描く。Semantics は `RoleLink`（Label は文字、Value は宛先、Tap の動作）。
- 公開の `Link` ウィジェットは別のブランチで作られているので依らない。上の振る舞いは `Link` の範囲（ホバーの下線、フォーカスリング、Enter、RoleLink）に合わせた。
- コードブロックは横の `Scroll` に入れ、折り返さない。高さは行数 × 行の高さで決める。タブは 4 桁ごとの空白に直す。
- 表は自前の RenderObject。列は一番広いセルの幅で、入りきらないときは比率で縮めて折り返す（ADR 0107 で、各列の最長の語の幅を下限にして残りを伸び代に比例して配る形に変えた）。列の幅は全部の行で決まるので、表がセル（孫）を直接レイアウトし、行は高さを受け取るだけにした。行には下限だけの制約を渡し、relayout boundary にならないようにしている（セルが変われば表がレイアウトし直す）。
- 画像は、段落の中で画像だけ（またはリンクで包んだ画像だけ）のものをブロックとして段落を分ける。文中のほかの位置の画像は代替テキストを出す。

Semantics: 見出しは `RoleHeading` と `Level`、リストは `RoleList` / `RoleListItem`、タスクは `RoleCheckbox`（`Checked` / `ReadOnly`）、コードブロックは言語名をラベルにした `RoleGroup`、表は `RoleGrid`（`ReadOnly`、`RowCount` / `ColumnCount`）と `RoleRow` / `RoleColumnHeader` / `RoleGridCell`。静的な表の役割は semantics に無いので `RoleGrid` を使った。

### 6. 壊れた入力・悪意のある入力

- 入力は先に整える: 不正な UTF-8 と NUL は U+FFFD、CRLF と CR は LF。
- 引用とリスト項目の入れ子は 32 段まで。それより深い `>` や `-` は文字として扱う。木の深さ（とウィジェットの深さ）が入力の長さに比例しない。
- 素朴に書くと 2 乗になる箇所を潰した: コードスパンの閉じは長さごとの位置の表を二分探索、`<` の自動リンクは空白か `<` で探索を止める、テキストの連結は 1 回でまとめる、深い字下げの行は空白の連なりを 1 回だけ測る、表の見出しは段落の最後の行だけを見る。リンクの宛先の括弧は 32 段まで（仕様どおり）。
- `FuzzParse`（seed にすべての書き方と病的な入力）と、3 万文字規模の病的な入力 25 種の時間のテストを置いた。60 秒の fuzz で 900 万回超を通した。

## 結果

- 本体のファイルは何も変えていない（go.mod / go.sum / `.golangci.yml` も）。lint の設定は入れ子のモジュールでもルートのものがそのまま効き、`markdown/` で `golangci-lint run ./...` が通る。
- テストは GPU 無しで通る。パーサは CommonMark 風の表テスト（約 140 件: 見出し、段落、フェンス、閉じないフェンス、字下げの混在したリスト、強調の区切りの規則、欠けたセルの表、CRLF、日本語）、ウィジェットは公開の `gowakutest` で（`widgets/internal/wtest` は本体の internal なので使えない）、リンクのタップ・キーボード・スクリーンリーダー、行をまたぐリンク、作り直しで解析しないこと、Highlight と ImageProvider を確かめる。

## 残したこと

- `*強調*` は `Italic` を指定するだけ。斜体の書体を持たないフォント（既定の日本語フォント）では、テキスト層が字形を約 12° 傾けて合成する（ADR 0101）ので、日本語と英語の混ざった強調も揃って傾く。縦書きの段落、カラー絵文字、右から左の文字は傾かないので、そこでは強調が見た目に出ない。`TestMarkdown_EmphasisIsVisible` が既定のフォントで強調と地の文の画素が違うことを確かめる。
- 名前付きの文字参照は約 40 個だけ。
- 選択とコピーは ADR 0105 で入れた（`field.SelectionArea` で囲む）。
- 見出しへのアンカーは ADR 0106 で入れた（`[x](#見出し)` で文書内を移り、`Controller` で見出しの一覧と移動）。
- 表は横スクロールしない。語すら入らない狭さでは語の途中で折れる（ADR 0107）。

## 追記（2026-11-13）: 画像を自分で読む

最初の版は画像を `ImageProvider` に任せきりで、何も渡さないと代替テキストしか出なかった。見本ですら画像が出ず、「Markdown を渡せば表示される」という期待に届いていなかったので、`Images fs.FS` を足した。

- 画像の参照が相対パス（`logo.png`、`./img/a.png`、`/img/a.png`）なら `Images` から読み、`paint.DecodeImage`（PNG / JPEG / WebP）で絵にして `basic.Image` で出す。大きさは絵そのまま、文書の幅より広ければ縦横比を保って縮める（`shrinkBox`。`basic` に幅から高さを決める部品が無いので、モジュールの中に置いた）。
- `fs.FS` にしたのは、ディスク上の文書（`os.DirFS`）と、プログラムに埋め込んだ文書（`embed.FS`）を同じ口で扱え、根より上（`../`）に出られないことを `fs.ValidPath` が保証するから。スキームのある宛先（`https:`、`file:`、`data:`）、`//` で始まるもの、`?` `#` `\` を含むものは読まない。
- **ネットワークからは今も取得しない**。文書を開いただけで外へ通信するのは、利用者のアプリが決めること。要るなら `ImageProvider` で渡す。`ImageProvider` は `Images` より先に聞かれ、nil を返した画像だけが `Images` に回る。
- 読むのは最初に表示するときの 1 回で、結果（読めなかったことも）は State に持つ。UI のスレッドで同期に読むので、巨大な画像には向かない。非同期の読み込みと差し替えは入れていない。
- 読んだ絵は `Source` が替わるまで持つ。`Images` が替わったことは見ない。`fs.FS` は比較できない型のこともあり（`fstest.MapFS` はマップで、`==` は panic する）、比較できるか調べるには `reflect` が要るが、規約（CODING_STYLE §5.2）は core の外での `reflect` を禁じている。ディスク上のファイルを書き換えても、同じ文書を表示している間は古い絵のまま。
- SVG とアニメーション GIF は読まない（代替テキストになる）。`basic.SVG` が正方形にしか描けないため。（ADR 0119 で SVG は読むようになった。`layout.RenderSVG` を任意の大きさの箱で使う）
