# 0078: ListView の中身から測る高さ

決定日: 2026-11-10

状態: 採用。表の上端の型は ADR 0150 で float64 に変えた

## 背景

ListView の行の高さは、ADR 0034 で次の 2 つにした: 固定の `ItemExtent` と、呼び出し側が事前に高さを返す `ItemExtentOf`。当初の計画の性能項目には「中身から測る高さのキャッシュと、高さ不定時の高速ジャンプ」が残っていた。折り返すテキストの行のように、組んでみないと高さが分からない行のためである。検討して作ることにした。

## 決定

### 1. API

- `ListView.MeasureItems bool`: 行を幅 W、高さ 0〜∞ で組み、その高さを使う。`ItemExtentOf` があればそちらが優先し、これは無視する。
- `ListView.EstimatedItemExtent float32`: まだ組んでいない行の高さ。0 なら、測った行の平均を使う（行が 1 つも無いうちは ItemExtent の 48）。
- `ListView.Controller *ListController`: ゼロ値で使え、3 つのモードのどれでも動く。
  - `JumpToIndex(i, align)`: align は 0 で上、1 で下、0.5 で中央。
  - `JumpToEnd()`。
  - `Remeasure(i)` / `RemeasureAll()`: 見えていない行の中身が変わったときに呼ぶ。
  - リストが付く前に頼んだジャンプは、付いた時点で行う。だから `InitState` で `JumpToEnd()` を呼べば、チャットを末尾から開ける。
- `layout.MeasuredExtents`: 高さの表。`layout.RenderList.Measured`、`OnShift`、`Reveal`、`StopRevealing` も足した。

### 2. 表: 2 本の Fenwick 木

- 各行の高さを float32 で持つ。-1 は未計測。
- 測った高さの和（float64）と、測った行の数（int32）を、それぞれ Fenwick 木に持つ。1 行あたり約 16 バイト。
- 行の上端は、測った高さの和に、未計測の行の数×見積もりを足したもの。オフセットにある行は、木を 1 回降りれば求まる。各節の幅は「和 +（長さ − 数）× 見積もり」になる。未計測の行は見積もりがすべて同じなので、これが成り立つ。
- 引く、位置から行を求める、更新する、忘れる、はどれも O(log n) でアロケーションしない。見積もりは問い合わせのときに掛けるので、変えても費用は無い。
- `Resize` は倍々に広げ、木を O(n) で作り直す。ItemCount が変わったときだけ起きる。
- 採らなかった: 前からの和の平らな配列。1 行測るごとに O(n) かかる。

### 3. 見積もり

- 呼び出し側のヒントがあれば、それを固定で使う。無ければ、測った行の移動平均を使う。最初の値は ItemExtent。

### 4. アンカー: 測り直しても中身が動かない

- 行を並べるたび（スクロールの各フレームとレイアウト）、最初に見えている行と、その画面上の上端を覚える。
- 次のレイアウトで組んだ行を測り直したら、offset = Offset(アンカー) − 上端 にする。見えている行は動かず、動くのはオフセットのほう。
- `OnShift` で、進行中の慣性（glide や spring）も同じだけずらす。そうしないと引き戻される。
- 古い行が 1 つも見えていない場合（スクロールバーをドラッグした後など）は、高さが変わる前にオフセットにあった行をアンカーにする。
- ジャンプの `Reveal` は、利用者がホイールかバーでスクロールするまで、アンカーより優先する。

### 5. ジャンプ

- 見積もりのオフセットへ跳び、そこにある行を作る。render object がターゲットとその周りを測り、正確な位置へ直す。
- 直した後に足りない行は、フレームの Build / Layout の繰り返し（NeedsBuild、最大 3 回）で、同じフレームの中で埋まる。
- 組むのは見えている行の周りだけ。10 万行の上でつまみを 50 段ドラッグしても、測るのは止まった所だけ（テストで 1,530 行未満）。

### 6. いつ忘れるか

- 親が作り直しても、ItemCount が変わっても、高さは添字ごとに残す。ItemCount が増えれば前の部分を残し、減れば切り詰める。
- 幅が変わったら全部忘れる。アンカーは保つ。
- 見えている行は何もしなくてよい。中身が変われば組み直され、高さを無制限で組んでいるので、その変化がリストに届く。見えていない行は `Remeasure`。
- 採らなかった:
  - 親が作り直すたびに全行を測り直す（ADR 0034 の規則 a-2）: O(n) のレイアウトになる。
  - 作り直しで表を消す: そのたびにスクロールバーが跳ぶ。

### 7. スクロールバー

- スクロールバーの Content は平滑化しない。つまみのドラッグは「割合 ×（Content − View）」で位置を求めるので、平滑化した値だと食い違う。
- アンカーがあるので、つまみがずれるのは見積もりの誤差の分だけ。ドラッグで 0.5 に置いた後、0.49〜0.51 に収まる（テスト）。

## 性能（i7-12700H）

| ベンチ | 結果 |
|---|---|
| 10 万行の折り返しテキストを定常スクロール | 1 フレーム 656〜683ns、0 allocs/op。高さ表の 1 万行は約 766ns |
| 中央へのジャンプ（1k 行） | 1.33〜1.44ms |
| 中央へのジャンプ（10 万行） | 1.19〜1.51ms |
| 末尾へのジャンプ（10 万行） | 0.95〜1.12ms |
| 固定の高さで中央へジャンプ | 1.66〜1.84ms |

ジャンプにかかる時間は行の数に依らない。中身は、測ることよりも、行を作ってテキストを整形することである。

## 残したこと

- ListView 自体にキー操作と Semantics は無い（ADR 0034 から変わらない）。PageDown や End は、アプリが ListController に結ぶ。
- 末尾に行が足されても末尾に張り付き続ける機能は無い。`JumpToEnd` は、その時点の最後の行をアンカーにする。
- 見本: `go run ./examples/listview -measured`（10 万行の折り返しテキスト）。
