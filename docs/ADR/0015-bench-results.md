# 0015: ベンチの方法と、負けた項目の扱い

決定日: 2026-11-07

状態: 採用

## 背景

当初の計画は Phase 8 の判断点として「ベンチで Cogent Core / Gio に負けた項目をどう扱うか」を置き、数字をそのまま載せて原因と対策を ADR に書くと決めていた。結果は [BENCH.ja.md](../BENCH.ja.md)。

## 方法の決定

- **`examples/bench` は別モジュールにする。** 本体の `go.mod` に Gio と Cogent Core の依存を入れない。ハーネスは OS の API を直接呼ぶが、ライブラリの一部ではないので、規約 §8 の境界の外に置く。
- **外から測る。** CPU、GPU、メモリは OS のカウンタで読み、3 者を同じ扱いにする。フレームの時刻だけは各プログラムが記録する。
- **ウィンドウを最前面に置き、マウスから遠い隅へ動かす。** 隠れたウィンドウは描画を止めることがある。実際のマウスが触れると hover で描き始める。
- **リサイズはドラッグではなく `SetWindowPos`。** ドラッグは実際のマウスを奪う。`WM_SIZE` の経路は同じだが、モーダルループは測っていない。
- **電力は比較に使わない。** RAPL はマシン全体の値で、同じ条件で 10〜18W ばらついた。

## 負けた項目の原因と対策

| 項目 | 原因 | 確かめ方 | 対策 |
|---|---|---|---|
| リサイズのメモリ 680MB | 4x MSAA のカラーと深度を毎回作り直す。古い分はドライバがすぐ返さない | `Samples: 1` で 236MB、CPU も 17.5% から 12.2% へ | 小さくするときは作り直さず、大きいターゲットのビューポートを狭めて使う。増やすときは余裕を持たせる。v1 ではしない |
| スクロールの GPU が Gio の約 2 倍 | 全画面の 4x MSAA と推定。**未確認** | 上の測定は resize のみ | MSAA が要るのはパスと形のあるクリップだけ。SDF の矩形と文字には要らない。当初の計画のレイヤーキャッシュとあわせて、MSAA のパスを分ける |
| 起動が Gio より 31ms 遅い | フォント索引の読み込み 40ms と、最初の日本語シェイピング 45ms | 段階ごとの計時 | 最初の日本語の文字を見てからフォントを読んでいるので、ウィンドウの作成と並行して別ゴルーチンで読む |
| 常用メモリが Gio より多い（215MB 対 158MB） | 日本語フォントの解析で 42MB のヒープ。残りは MSAA のターゲット | `runtime.MemStats` | 上の 2 つで減る |
| アニメーションが 10 秒に 5 フレーム落ちる | **未解明。** GC ではない（`GOGC=off` でも 596 フレーム） | 落ちるのは目標が変わる瞬間の周辺と見ているが、未確認 | v2 の前に追う |
| 受けたサイズの数が Gio より少ない | 1 回の `Resize` が重い。MSAA の作り直しで同じ原因と推定 | `Samples: 1` でも 269 回で変わらなかったので、**推定は外れている可能性が高い** | ピーク時の所要時間を分解する |

## 決定

- 数字は手を加えず README と BENCH.md に載せる。

## 追記: 最適化の結果（2026-11-07）

上の表の対策のうち 2 つを v1 のうちに実施した。当初は「公開の直前に描画の経路に手を入れない」として v2 に送ったが、最適化の依頼を受けて前倒しした。

| 項目 | 前 | 後 | 何をしたか |
|---|---:|---:|---|
| リサイズのメモリ（MB） | 680 | 247 | MSAA を要るフレームだけにした（ADR 0017） |
| スクロールのメモリ（MB） | 215 | 175 | 同上 |
| スクロールの GPU（%） | 7.2 | 4.3 | 同上。Gio と同じになった。推定は当たっていた |
| リサイズの CPU（%） | 17.5 | 12.2 | 同上 |
| 起動（ms） | 197 | 162 | フォントを並行して読む（ADR 0018） |
| アニメーションのフレーム | 595 / 600 | 600 / 600 | 3 回とも落ちなくなった |

フレーム落ちが消えた理由は確かめていない。MSAA の resolve が無くなったからと見ているが、同じ変更に `Post` の修正なども入っている。

**残っている差**

- メモリは Gio より多い（175MB 対 160MB、247MB 対 165MB）。日本語フォントの解析のヒープが約 40MB。
- 受けたサイズの数が Gio より少ない（53 対 60）。原因は未解明。

**これ以上やらなかったこと**

CPU の内訳を `QueryProcessCycleTime` と `QueryThreadCycleTime` で測った。`GetProcessTimes` は約 15.6ms 刻みで、vsync に同期した処理では 1.5〜3% ぶれるので、この規模の比較には使えない。

| スレッド（Mcycles/s） | `Present` だけ | `gowaku.Run` |
|---|---:|---:|
| メイン（`Present` を含む） | 90 | 79 |
| Go ランタイムの別スレッド | 11 | 31 |
| Intel ドライバのスレッド（`igd10um64xe.dll`） | 16 | 28 |
| 合計 | 119 | 142 |

全体の約 8 割は `Present` の経路で、gowaku の上乗せは約 2 割。Go のツリー処理は 1 フレーム約 5µs（6 回の割り当て）で、上乗せの大半は説明できない。増えているのはドライバと Go ランタイムで、Go のスレッドが何をしているかは特定していない。

毎フレームの深度クリアを省く案は試したが、差が出なかったので戻した（中央値 132.9 と 133.5）。`GOMAXPROCS` の変更はアプリのゴルーチンの並列性を変えるのでしない。`ListView` の行の再利用なども効果が測れないのでしなかった。

## 結果

当初の計画の「4K でリサイズしても CPU が上がらない」は、4K の画面が無いので確かめられていない。この主張は README に書かない。実機で測ったら BENCH.md を更新する。
