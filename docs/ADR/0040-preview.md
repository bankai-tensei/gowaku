# 0040: プレビューはファイルとコマンドを土台にし、ページを上に載せる

決定日: 2026-11-08

状態: 採用

## 背景

SwiftUI や Compose のプレビューに当たるものが欲しい、という要望が出た。何で見せるかを話し合ううちに、使うのは人だけではない、という点がはっきりした。この開発では、AI エージェントが UI を確かめる流れがずっと次のようになっていた。

1. gowakutest で PNG を書く。
2. エージェントがその PNG を読む。
3. `Dump` の文字で木を見る。
4. `cmp` で前回と比べる。

エージェントにとって扱いやすいのは窓ではなくファイルで、gowaku の専用の窓はスクリーンショットを撮らないと見えない。また、この流れには次の 3 つが欠けていた。

- 前回とどこが変わったかを示すもの
- アニメーションの途中のコマ
- 機械が読める警告（はみ出し、ラベルのない操作部品、コントラスト不足）

## 選択肢と決定

### 表示の場所

| 案 | 人 | AI | 手間 |
|---|---|---|---|
| ファイル（PNG と JSON） | △ | ◎ | 小 |
| ローカルのウェブページ | ◎ | ○ | 小〜中 |
| gowaku の専用の窓 | ○ | ✕ | 中 |
| VS Code の拡張 | ◎（VS Code の人だけ） | △ | 大 |

**ファイルとコマンドを土台にし、人のためのページをその上に載せる。** 専用の窓は、ページから 1 つのプレビューを実際の窓で開いて触る用途（`-live`）に限る。MCP サーバーで包む案は、コマンドがあれば今の AI はすでに使えるので後回しにする。

### プレビューの書き方

`_test.go` に置く `func PreviewXxx() Widget` か `func PreviewXxx() gowakupreview.Item` にする。`Example` 関数と同じ考え方である。

- テストのビルドにしか入らないので、アプリの実行ファイルは大きくならない。
- 同じパッケージなので、非公開の部品も呼べる。見本アプリ の部品は大半が非公開だった。

`PreviewTheme() ThemeSet` を置くと、そのパッケージの全プレビューのテーマになる。プレビューの中でテーマを読むために、`widgets.Builder{Content: func(ctx) Widget}` を足した（Flutter の `Builder` に当たる）。

### 動かし方

コマンド `cmd/gowaku-preview` は、次の順で動く。

1. `go/parser` でテストファイルからプレビューを集める。
2. それらを呼ぶテストを生成し、**`go test -overlay` で差し込む**。利用者のフォルダーにはファイルを 1 つも書かない。
3. 生成したテストが `gowakupreview.Run` を呼び、gowakutest で描く。

出力先とプレビューの絞り込みは、環境変数で渡す。

- **描く内容：** ライトとダークで描く。`Widths` を指定すれば幅ごとに描き、`At` か `-at` を指定すれば途中のコマも描く。
- **大きさ：** `Width` と `Height` を指定しなければ、最大 1600×1200 の中で描いてから中身の大きさに切り出す。
- **書き出すファイル：** 描いたものごとに PNG を書く。前回と違えば `.diff.png`（変わった画素を赤、それ以外を薄い灰色で示す）を書く。パッケージごとに `report.json` と `report.txt` を書き、Semantics の木と警告を載せる。
- **パニックしたとき：** プレビューがパニックしても、`recover` はしない（規約）。テストは失敗し、スタックが出る。レポートはプレビューを 1 つ描くごとに書くので、それより前の結果は残る。
- **`-watch`：** `.go` ファイルの更新時刻を 400ms ごとに見る。fsnotify には依存しない。
- **`-http`：** 状態を JSON で返す API と、それを 700ms ごとに読みに行くページを出す。ページは、警告の矩形を画像の上に重ね、差分の表示に切り替えられ、「窓で開く」ボタンを持つ。

### 警告（gowakutest.Tester.Warnings）

プレビューとは別に、gowakutest 単体の機能として足した。

- **overflow：** `RenderFlex` と `RenderParagraph` に、レイアウトのときに分かるはみ出しの量を返す `Overflow()` を足した。アロケーションは増えない。
- **unlabeled：** ボタン、チェックボックス、スライダー、テキスト欄のうち、ラベルがなく、子にも文字がないもの。
- **contrast：** WCAG 2 の比で判定する。普通の文字は 4.5:1、大きな文字は 3:1 を下回れば警告する。背景の色は、文字の箱の中の画素から、文字の色に近い画素を除いた最頻色で求める。色は粗い段階でまとめて数える。グラデーションの上の白い文字が自分の色と比べられて 1.00:1 と出る誤検出は、こうして直した。

隠れた部分木（不透明度 0 など）は調べない。木をたどるために、`core.Tree.RootRenderObject` と `RenderParagraph.Text` / `Style` を公開した。

## 結果

- 見本アプリ の 7 プレビュー（14 枚）を描いた。初回は 21 秒、2 回目からは 1 プレビューあたり約 6 秒かかる。大半は `go test` の結合（リンク）の時間で、何も走らせない `go test` でも 4.6 秒かかる。システムフォントの読み込みは初回の 110ms だけ。
- 早速、次の 2 つを見つけた。
  - 統計ページの数字のタイルが、幅 760 で 18〜50px はみ出していた。`Grid` に替えて直し、ページが自動で描き直されて警告が消えるところまで確かめた。
  - テーマの `Ink3` は、白地で 2.5:1、黒地で 3.5:1 しかない。時刻の表示、グラフの目盛り、順位の数字などが WCAG AA に届かない。テーマの色をどうするかは別に決める。
- 描き直しの速さは SwiftUI のプレビューと同じくらいの体感で、Flutter のホットリロードの即時性には届かない。
