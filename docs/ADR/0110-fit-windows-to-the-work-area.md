# 0110: 開くウィンドウを作業領域に収める

決定日: 2026-11-13

状態: 採用

## 背景

「このフレームワークで作るとウィンドウが大きく出る。DPI は効いているのか」という報告を受けた。

調べると、DPI は正しく効いていた。Win32 は Per-Monitor V2 を宣言し、`WindowOptions` の `Width`/`Height`（論理ピクセル）を `GetDpiForWindow` の倍率で物理ピクセルに直し、`AdjustWindowRectExForDpi` で枠を足している。

原因は画面の側にある。報告した環境は物理 1920×1200 で、拡大率は 150% だった。論理ピクセルにすると、デスクトップ全体でも 1280×800 しかない。

- 既定の 800×600 は、作業領域の高さのおよそ 8 割になる。
- Inspector の 1180×780 は、画面ほぼいっぱいになる。
- 作業領域より大きいサイズを渡すと、ウィンドウはそのまま画面の外へはみ出していた。
- `CW_USEDEFAULT` の位置は、ウィンドウの大きさに関係なく右下へずれていく（カスケード）。そのため、収まる大きさでも下端が切れることがあった。

作業領域を見ていたのは、所有されたウィンドウを親の上の中央に置く `centerOver`（ADR 0047）だけだった。

## 決定

### 1. 開くときの大きさを作業領域の 90% までに切り詰める

`setClientSize` で、枠を含めたウィンドウの幅と高さを、それぞれモニターの作業領域（`MONITORINFO.rcWork`）の 90% までに抑える。縦横比は保たない。軸ごとの `min` にすると、指定値から連続に変わり、収まる指定は 1 ピクセルも変えないで済むため。

選択肢:

1. 作業領域ちょうどまでに抑える。最大化と見分けがつかず、端をつかんで動かせない。
2. 作業領域の 90% までに抑える（採用）。
3. 既定の 800×600 だけを小さくする。指定された大きさがはみ出す問題が残る。

- `setClientSize` は作成時と `place`（DPI が違うモニターへ置いたとき）からしか呼ばれない。そのため、ユーザーがあとで広げた大きさは切り詰めない。
- 値は `workAreaShare = 90`（百分率）として定数にした。

### 2. 既定の位置では作業領域の中へ動かす

所有者が無く、`Placed` でもないウィンドウは、大きさを決めたあとで `fitInWorkArea` を呼ぶ。作業領域からはみ出していたら中へずらす。はみ出していなければ動かさない（OS のカスケードを保つ）。

- `Placed`（タブを引きはがしたときなど、ポインターの位置に開くウィンドウ）は、アプリが選んだ位置なので動かさない。
- 所有されたウィンドウは、これまでどおり `centerOver` が作業領域へ収める。
- `centerOver` の作業領域の取得を `workAreaOf(hwnd)` に切り出し、両方から使う。

## 範囲

Win32 だけ。macOS は OS が開くウィンドウを画面の中へ収める。X11 は `_NET_WORKAREA` を読めば同じことができるが、報告が無く、ここでは確かめられないので、今回は手を入れない。Wayland はコンポジタが大きさと位置を決める。

## 確かめたこと

- `//go:build gpu` のテスト `TestCreateWindow_FitsTheWorkArea`。10000×10000 は作業領域の中に収まって 90% 以下になり、320×200 は大きさが変わらない。
- 実機（1920×1200、150%）で 1180×780 を指定すると、ウィンドウは 1728×1080（作業領域の 90%）になり、画面の中に開いた。
