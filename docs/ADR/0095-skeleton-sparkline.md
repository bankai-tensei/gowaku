# 0095: 読み込み中の骨組み（Skeleton）と小さなグラフ（Sparkline）

決定日: 2026-11-13

状態: 採用

## 背景

当初の計画の `Skeleton`（B: 小さく作れる）と `Sparkline`（C: 範囲を決めてから）。Skeleton は「シマーは ReduceMotion で止める」、Sparkline は「Table のセルに入る折れ線と棒まで。軸や凡例を持つチャートは作らない」と当初の計画に書いてある。Phase 18 の部品として、ほかの 9 つと並行して作った。

## 決定

### 1. 置き場所

- どちらも `widgets/control`（段 3）に置いた。`ProgressRing` と同じく、自前の見た目を持ち、入力を受けない表示の部品。描画オブジェクトは公開せず、パッケージの中に持つ（`renderSkeleton`、`renderSparkline`）。

### 2. Skeleton の API

- `Skeleton{Shape, Width, Height, Radius}`。形は `SkeletonLine`（ゼロ値。高さ 12 の錠剤、幅は親が許すだけ）、`SkeletonBlock`（高さ 64、角は Control の 8）、`SkeletonCircle`（直径 32）。
- `SkeletonText{Lines, Spacing}` が「N 行の幅の違う行」の補助。行の幅は 1, 0.94, 0.86, 0.97, 0.9 の繰り返しで、2 行以上なら最後の行を 0.6 にする（段落の最後の行が短いのと同じ）。補助を関数ではなくウィジェットにしたのは、規約 §5.3 の補助関数（構造体を返すだけの 1 行）に収まらないから。
- `SkeletonGroup{Label, Child}` がスクリーンリーダーへの窓口。`RoleProgress`（Range 無し＝量の分からない読み込み中）で、ラベルは `Label`、無ければ `Strings.Loading`（「読み込み中…」）。中は訪ねない。骨組みの形そのものは何も言わない。
  - `semantics` に Busy の状態は無い。足すと platform（UIA、AT-SPI、macOS）の対応が要るので、今ある RoleProgress で表した。
- 色: 地は `FillStrong`。光はライトでは地を薄く（α×0.4）、ダークでは濃く（α×1.8）する。どちらも「明るくなる」方向。ベージュや色付きの光は使わない。

### 3. シマー

- グラデーションで描く。`ShaderMask` は使わなかった。
  - ライブラリにシマーのシェーダーは無い（`examples/shader` の `shimmer` は例で、gpu/soft の Fallback を利用者が持つ形）。新しいシェーダーを足すと HLSL・SPIR-V・MSL の生成物と soft の式が要る。
  - `ShaderMask` は子をレイヤーに描いてから読むので、1 つの骨組みごとにレイヤーのページを使う。3 ストップの線形グラデーションなら `DrawRRect` 1 回で済み、`Op` の固定長の `Stops` に収まるのでアロケーションも無い。
- 形ごとに `DrawRRect` 1 回。3 ストップ（地、光、地）の線形で、帯の外は端の色（地）が続く。帯の幅は 240、1 周 1.6 秒。
- **全部の骨組みで光をそろえる:** 位相はティッカーの時刻から計算する（`now % 1.6s`）。1 つの木のティッカーは同じフレームに同じ時刻をもらうので、共有の状態を持たなくても位相がそろう。帯の位置はウィンドウの座標で決め（`core.LocalToGlobal` で自分の x を引く）、帯がウィンドウを左から右へ横切る。だからカードの中の円と行は、1 本の光が順に通るように見える。ウィンドウの幅は根の描画オブジェクトの大きさで、親をたどって取る（アロケーション無し）。
- **見えている間だけティッカーを回す:** 描画オブジェクトのティッカー（`RenderBase.NewTicker`）を、`Paint` で形が実際に記録されたときにだけ動かす。
  - `Paint` の前後で `DisplayList` の命令の数を比べる。`Canvas` はクリップの外や透明な形を記録しないので、スクロールの外、`ClipRect` の外、透明な `Opacity` の下では数が増えない。そのときはティッカーを動かさない。
  - ティックで `painted` を見て、前のティックから一度も描かれていなければ止める。祖先が描くのをやめた（`Opacity` が 0、一覧の外に出た）ときも、次のティックで止まる。見えるようになって描かれれば、また動く。
  - 木から外れたら（`Attached` が false）次のティックで止まる。大きさゼロの形は描かないので動かない。
  - `shaderClock` のように 200ms ごとに見直すことはしない。描かれなければ二度と起きないが、見えるようになるときは必ず祖先が描き直すので要らない。
- **ReduceMotion:** `MediaQuery.ReduceMotion` を読み、光を止めて地の色だけで描く。走っている途中で切り替わったら、`UpdateRenderObject` でティッカーを止める。
- 光が始まる前（最初のティックの前）の 1 フレームは地の色だけで描く。描画の中で今の時刻を知る方法が無いため。

### 4. Sparkline の API

- `Sparkline{Data []float64, Kind, Min, Max, Width, Height, Color, Negative, Thickness, Fill, MarkLast, Label}`。
  - `SparklineLine`（ゼロ値）と `SparklineBars`。
  - 範囲は Data の最小から最大、`Max > Min` ならその範囲で、外は端に寄せる。棒は 0 も範囲に含め、ゼロの基線から上下に伸ばす。負の値の棒は `Negative`（既定は `Danger`）。範囲が 0 をまたぐときは、基線に `Hair` の細い線を引く。
  - 線は `AccentInk`（細い線用の色）。幅は 1.5。`Fill` は線の下を上から下へ薄くなるグラデーションで塗る。`MarkLast` は最後の有限の値に点を置く（線だけ。棒には何もしない）。
  - 大きさは `Width`/`Height`、ゼロなら親が許すだけ、無制限なら 64×20。線と点が切れないよう、線の太さの半分（点があれば点の半径）だけ内側に描く。
- NaN と ±Inf は欠け: 線はそこで切れ（新しい輪郭になる）、棒は抜ける。1 点だけの区間は、丸いキャップの点として描かれる。面は 2 点以上の区間だけ塗る。
- 空の Data、全部 NaN、大きさゼロのセルは何も描かない。一定の値は真ん中を通る水平線。
- **作らないもの:** 軸、目盛り、凡例、ツールチップ、ホバー、選択、アニメーション、複数系列、チャートの枠組み。当初の計画のとおり。

### 5. Sparkline のアロケーション

- 線と面の `paint.Path` は描画オブジェクトのフィールドに持ち、ウィジェットが変わったとき（`UpdateRenderObject`）か大きさが変わったときにだけ作り直す。作り直しも `Reset` して同じ記憶域に足すので、伸びきればアロケーションは無い。`Canvas` は経路を写すが、その記憶域も使い回される。
- 棒は経路を使わず、毎回 `DrawRRect` で描く（計算だけ）。
- `Paint` はグラデーションと線の `Stroke` をフィールドに持って、そのアドレスを渡す。
- Data は写さずに読む。中身をその場で変えたら、ビルドし直す（doc コメントに書いた）。`UpdateRenderObject` は毎回描き直しを頼む（中身が変わったかは分からない）。
- スクリーンリーダーの要約は `Semantics` の中でだけ作る（文字列の連結が要るので、描画の道には置かない）。
- 計測（このマシン、Windows、`go test -bench`）:
  - `BenchmarkSparkline_Paint_1kRows`（1000 行、線と棒が交互、毎フレームずらして描く）: 約 0.6〜1.2 ms/op、0 B/op、0 allocs/op。
  - `BenchmarkSparkline_Recycle_1kRows`（仮想化された表のスクロールのように、毎フレーム全行が別の系列を見せ、線を作り直してから描く）: 約 1.4〜2.6 ms/op、0 allocs/op。
  - `BenchmarkSkeleton_ShimmerFrame`（カード 1 枚のティック、レイアウト、描画）: 約 0.76 µs/op、0 allocs/op。
  - どれも PC の揺れで 2 倍ほど変わる。

### 6. Sparkline のアクセシビリティ

- `RoleImage`。ラベルは `Label`、無ければ「最小 3, 最大 12, 最新 8」のような要約（`Strings.Minimum`、`Maximum`、`Latest`）。数は小数 2 桁までに丸め、余計な 0 は付けない。データの意味（単位や傾向）は呼び出し側にしか分からないので、`Label` を渡すことを勧める。

## 結果

- テスト（GPU 無し）: Skeleton は形と大きさ、`SkeletonText` の行の幅、`SkeletonGroup` の読み込み中のノードと中を隠すこと、光がそろって右へ動くこと、ReduceMotion で最初から止まることと途中で止まること、木から外れたら・スクロールの外・透明な Opacity の下・大きさゼロでフレームを頼まないこと、透明から戻ったら再び動くこと、描画のアロケーション 0。Sparkline は空・1 点・一定・負・NaN・全部 NaN・面・点・範囲の固定・棒の基線と負の棒・細いセルの隙間・大きさゼロのセル・無制限の大きさ・要約（英日）・中身の変更が描き直しに出ること、描画と作り直しのアロケーション 0。
- gallery の `pages_visual.go` に、読み込み中のカードと読み込んだ後のカードを並べ、スイッチで切り替える例と、スパークラインの小さな表を置いた（表は ADR 0100 で `collection.Table` になった）。

## 残したこと

- 決めた時点では `collection.Table` にウィジェットのセルが無く、Sparkline を本物のセルに入れられなかった。gallery の表は `Row` と `Divider` で組んでいた。その後 ADR 0100 で `Table` にウィジェットのセル（`CellWidget`）を足し、Sparkline は `Table` のセルに入るようになった。gallery の表も `collection.Table` に置き換えた。
- Skeleton の光は、ウィンドウを横切る 1 本の帯だけ。斜めの帯、波の形、色付きの光は持たない。
- 骨組みから本物の中身への切り替えのアニメーション（フェード）は持たない。`basic.AnimatedSwitcher` と組み合わせる。
- `semantics` に Busy の状態を足すかは、platform の対応と一緒に別に決める。
