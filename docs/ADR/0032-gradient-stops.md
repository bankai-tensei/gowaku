# 0032: グラデーションのストップを 4 つまで、インスタンスに直接持たせる

決定日: 2026-11-08

状態: 採用

## 背景

公開 API だけで音楽プレーヤーの見本アプリを書いたところ、アルバムのジャケットやヒーローカードで 3 色目（紫 → ピンク → オレンジ）が欲しくなった。`paint.Gradient` は 2 色（ADR 0005）なので、グラデーションを 2 枚重ねるか、3 色目を諦めるしかなかった。

当初の計画は v2 の複数ストップを「1D テクスチャ」で作る想定だった。

## 選択肢

### 色の渡し方

- (a) ストップの色をランプにして、1D テクスチャ（またはアトラスの 1 行）に焼く。
  - ストップ数に上限が無い。
  - ただ、グラデーションごとにテクスチャの領域を確保・解放する仕組みが要る。
    - フレームをまたぐキャッシュと、その鍵（ストップ列の比較）が要る。
    - 描画コールのテクスチャ切り替えと束ね方が変わる（`addDraw` の `fits`）。
  - 焼いた解像度で色が段になる。
- (b) ストップの配列を構造化バッファ（Vulkan はストレージバッファ）に置き、インスタンスは添字だけ持つ。
  - 上限はほぼ無い。
  - D3D11 の SRV と Vulkan のディスクリプタを新しく足すことになり、両バックエンドの束縛の形が変わる。
- (c) 少ない固定数のストップを、インスタンスに直接持たせる。
  - 新しいリソースも束縛も要らない。Encode はアロケーションしない。
  - インスタンスが大きくなる。グラデーションを使わないグリフにも、増えた分がかかる。

### 上限

- 3 は今回の要望ちょうど。
- 4 なら、オフセットがちょうど `float4` 1 つに入る。
- 8 は、Vulkan が最低限保証する頂点出力（`maxVertexOutputComponents` = 64、つまり 16 ロケーション）を超える。
  - 今のヴァリイングは 9 ロケーション。
  - 4 ストップでは、色 2 つとオフセット 1 つで 12 になる。
  - 8 ストップでは、色が 6 つとオフセットが 2 つで 17 になる。

## 決定

**(c) で、上限は 4 にする。**

一般的な UI のグラデーションは 2〜3 色で、4 色あれば CSS の作例の大半が書ける。8 色はインスタンスの受け渡しだけでは作れないので、それが要るときは (a) か (b) に移る。

### API

`paint.Gradient` に `Stops [MaxGradientStops]GradientStop` と `StopCount int` を足す（`MaxGradientStops = 4`）。

- `StopCount` が 0（ゼロ値）なら、これまでどおり `StartColor` から `EndColor` へ。既存のコードはそのまま動く。
- 正なら、`Stops` の先頭 `StopCount` 個を使い、`StartColor` / `EndColor` は見ない。
- 最初のストップより前と最後のストップより後は、端の色が続く（CSS と同じ）。
- 前のストップより小さいオフセットは、前のオフセットまで引き上げる（CSS と同じ）。同じオフセットが 2 つ並ぶと硬い境目になる。
- `StopCount` が範囲外なら、`Canvas` が `panic("gowaku: ...")` で止める。

スライスにしなかったのは、`Gradient` を比較可能なままにするため。`layout.Decoration.Equal` は `==` で比べている。また、`Canvas` が不透明度をかけた写しを `Op` に入れるときに、アロケーションしないためでもある。

`Op` は `Gradient` を値で持つので、88 バイト大きくなる。

### インスタンス

`gpu.Instance` の末尾に、次の 2 つを足す。112 → 160 バイト。

- `MidColors [2]geom.Color`: 2 番目と 3 番目のストップの色
- `StopOffsets [4]float32`

既存のフィールドのオフセットは変えない。`Color` は最初のストップの色、`EndColor` は最後のストップの色になる。

- ストップが 4 つ未満のときは、足りない分を **先頭のストップの写しで前に詰める**（`gpu.Instance.SetStops`）。2 色は `(c0@0, c0@0, c0@0, c1@1)` になる。
- シェーダー（`sdf.ps.hlsl` の `ramp`、ソフトウェア版は `gpu/soft` の同名関数）は、分岐なしで 3 回の `lerp` を順にかける。
  - 各 `lerp` の重みは `saturate((t - o[i-1]) / max(o[i] - o[i-1], 1e-6))`。
  - 詰めたストップでは、同じ色どうしの `lerp` になるので何も変わらない。
  - 2 色の結果は、計算の上ではこれまでの `lerp(c0, c1, saturate(t))` と同じになる。ソフトウェア版で作り直した既存の golden は、PNG がバイト単位で変わらなかった。

D3D11 の入力レイアウトに `COLOR3` / `COLOR4` / `STOPS` を足した。Vulkan は頂点属性 8〜10 を足した。

インスタンスを手で作るテストは、`StopOffsets` のゼロ値では 2 色にならない。`SetStops` を通す。

## 結果

- golden に `gradients` を足した。
  - 対角の 3 色（紫 → ピンク → オレンジ）
  - 放射の 4 色
  - 両端に余白があり、中央に硬い境目がある 4 色
- D3D11 と Vulkan（HighPerformance）は、どちらも最大差 1 で同じ golden に収まった。
- Encode は 4 ストップでもアロケーション 0。
  - `BenchmarkEncode_10kRects` は、このマシンの最良値で約 0.47ms から約 0.63ms になった。インスタンスと `Op` が大きくなった分のコピーと見ている。
  - 並行して他の作業が走っていたので、計測のばらつきは大きい。
- GPU に送るバイト数は 1 インスタンスあたり 48 バイト増える。1 万インスタンスで 1.6MB/フレームで、帯域としては問題にならない。
- ADR 0005 の「インスタンスは 112 バイト」「グラデーションは 2 色」は、この ADR で置き換える。
- スイープグラデーション、5 色以上、`Transform` 付きのグラデーションは引き続き v2（当初の計画）。要るようになったら (a) か (b) を検討する。
- 追記（2026-11-09）：ADR 0044 §2 で、`MaxGradientStops` は 4 のまま、5 ストップ以上を `Gradient.MoreStops` で渡せるようにした。4 ストップまではこの ADR のまま。5 ストップ以上は (a) のランプのテクスチャで描く。スイープと `Transform` も足した。
