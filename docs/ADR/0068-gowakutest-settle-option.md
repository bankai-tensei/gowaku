# 0068: gowakutest の Settle の選択肢と、Find が古い木を見ていた件

決定日: 2026-11-09

状態: 採用

## 背景

サンプルのアプリを gowakutest で試したところ、2 つ詰まった。

- **止まらない木で Tap が使えない。** `Tap`、`TapAt`、`Type`、`Key` は最後に `Settle` を呼ぶ。`Settle` は何も動かなくなるまでフレームを描き、偽の時計で 1 分たっても動いていればテストを落とす。軌道の図を毎フレームの Ticker で回す State があると、木は永遠に止まらないので、これらは必ず落ちる。サンプルはポインタのイベントを手で送り、`Advance` を呼んでしのいだ。
- **画面にある文字が `Find` で見つからない。** Navigator のホームの、SplitPane の中の Scroll の中の Grid にある Pressable のタイル（Label は衛星の名前、中に Hero と Text）が、`tt.Find("いぶき 1 号")` で見つからなかった。同じテストの前のほうでは、SidebarItem や普通のリストの Pressable は見つかっていた。

## 決定

### 1. `Options.Settle time.Duration`

- `gowakutest.Options` に `Settle time.Duration` を足した。
  - 正の値のとき、`Tap`、`TapAt`、`Type`、`Key` は行動のあと、Settle する代わりに `Advance(Settle)` で時計をその分だけ進める。途中のフレームは `Advance` と同じく描く（何か動いていれば `FrameTime` ごと）。
  - 0 以下は今までどおり静止を待つ。既存のテストは何も変わらない。
  - 名前は、メソッドの `Settle` と同じにした。「Settle と言ったときに何をするか」を決める値なので、同じ名前のほうが読み手が結びつけやすい。`ActFor` や `Step` も考えたが、何の時間かが分からない。
  - doc には目安として 500ms を書いた。ページの入り（280ms）とダイアログの入りが終わる長さ。
- **明示的に呼んだ `Settle()` も、この値に従う。**
  - 止まらない木で、厳密な `Settle()` は必ず 1 分後に落ちる。役に立つ場面が無い。
  - テストの補助関数が `Settle()` を呼んでいることは多い。選択肢 1 つで、木全体を「止まらない木」として扱えるほうが分かりやすい。
  - 「この動きは終わるか」を確かめたいテストは、`Settle` を 0 のままにした別の Tester で書ける。止まらない部品を含む木では、もともと確かめられない。
- 0 のまま止まらない木で落ちたときのメッセージに、「永遠に動く木なら `Options.Settle` を設定する」と足した。

### 2. Find が前のフレームの木を見ていた

- **再現の結果。** 報告の形（SplitPane > Navigator > Scroll > Grid > Pressable > Row > Hero / Column > Text）をそのまま組み、Hero で詳細ページへ行って戻るところまで試したが、`Find` は毎回タイルを button として見つけた。Navigator、Hero、Grid、ラベルのまとめ方、照合の規則、Rect のどれにも誤りは無い。
- **原因。** `Find` は `Semantics()` を読み、`Semantics()` は**最後に描いたフレームの**レンダーオブジェクトをなめていた。テストが `Tree().DispatchPointer` で直接クリックを送ると、SidebarItem の `SetState` は汚れの印を付けるだけで、次のフレームまで木は作り直されない。サイドバーで「Fleet」に切り替えた直後の `Find` は、まだ前の区画を見ていた。前のほうで見つかった SidebarItem と普通のリストは、最初のフレームから木にあったので見つかった。
  - `Screenshot` は描く前にフレームを作るので、画像には新しい区画が写る。「画面にあるのに見つからない」はこの食い違い。
  - さらに `Advance(0)` は何も描かなかった（`for now < end` が一度も回らない）。「時計は進めずに 1 フレーム」のつもりで書いても、木は古いまま。
  - 報告の場面は手元に無いので、これが原因だったかは断定できない。ただし、報告の形で `Find` が失敗するのは、この方法と、見えないもの（下の一覧）を探したときだけだった。
- **直したこと。**
  - `Tester.Semantics()`（`Find`、`FindAll`、`Dump`、`Warnings` もこれを使う）は、前のフレームから変わったものがあれば、時計を進めずに build と layout を済ませてから木を読む。「次のフレームが見せるもの」を返す。Tick は呼ばないので、時間の止まった世界はそのまま。
  - `Advance(0)`（0 以下）は、今の時刻で 1 フレーム描く。`Pump` と同じ。
  - `Tap` が何も見つけられないときは、`Dump` の木をメッセージに付ける。ラベルの食い違いがすぐ分かる。
  - `Find` の doc に、見つからない理由になる規則を書いた。
    - ラベルは全体で一致する。読み上げと同じもので、`Dump` に出る。
    - 部品と同じことを言う中の文字は木に無い。`Find` は部品を返す。
    - Label の無いボタン（押せる Card など）は、中の文字を全部空白でつないだ名前になり、文字は単独では木に無い。
    - 見えないものも木に無い: Opacity 0（フェードインの始まりなど）、Navigator の上でないページ、畳まれたペイン。

## 結果

- 毎フレーム動く木でも `Tap`、`Type`、`Key` がそのまま使える。サンプルで手でイベントを送る必要は無くなった。
- 手でイベントを送るテストも、`Find` の前に `Advance` を忘れて迷うことが無くなった。
- テストは `gowakutest/settle_test.go`: 止まらない木での Tap / Type / Key / Settle と時計の進み方、0 のときの失敗のメッセージ、手で送ったクリック直後の `Find`、報告の形のタイル（Hero で行って戻る）、`Advance(0)`、`Tap` の失敗に木が付くこと。
- 残り:
  - `Semantics()` はフレームを作ることがある。描いた絵を変えずに古い木を見たいテストは、`Tree().Semantics()` を直接呼ぶ。
